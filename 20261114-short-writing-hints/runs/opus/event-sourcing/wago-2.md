# イベントソーシング入門

## 1. 概要

イベントソーシング（Event Sourcing）は、アプリケーションの状態変化を「イベント」単位で時系列順に記録し、イベント列の再生で現在状態を導出する設計パターンです。データベースの保存対象は、最新状態から状態変化の履歴全体へと転換します。

具体例として銀行口座を想定します。従来型の設計では、口座テーブルに「残額：3,000円」のみを保存します。イベントソーシング方式では「口座開設」「10,000円入金」「7,000円出金」の3件のイベントを保存し、残額3,000円は全イベントの順次適用で算出します。

イベントは過去に発生した事実の記録なので、原則として変更・削除は禁止です。データ構造はアペンドオンリー（追記専用）のログに該当します。

## 2. 従来型CRUD方式との比較

一般的なCRUD方式では、更新処理の際に既存レコードを直接更新します。結果として旧状態は消失し、変更理由や変更経緯の追跡は困難です。監査要件への対応目的で別途履歴テーブルを用意する設計も多数存在しますが、本体データと履歴データの整合性確保は開発者の責任です。

一方、イベントソーシングでは履歴が一次データ（Source of Truth）で、現在状態は派生データに相当します。両者の相違点を下表に整理します。

| 観点 | CRUD方式 | イベントソーシング |
|---|---|---|
| 保存対象 | 最新状態 | 状態変化の全履歴 |
| 更新方法 | 直接更新 | 追記のみ |
| 履歴情報 | 原則消失 | 完全保存 |
| 参照性能 | 高速 | 再生コスト発生 |
| 設計難易度 | 低 | 高 |

## 3. 主要構成要素

### イベント

イベントは「発生済みの事実」を表現するイミュータブルなデータです。命名は過去形が基本で、`OrderPlaced`（注文確定）、`ItemShipped`（商品発送）などが典型例です。各イベントにはイベントID、発生日時、集約ID、バージョン番号、ペイロードを付与します。

### イベントストア

イベントの永続化専用ストレージです。集約単位のストリームへのイベント追記と、ストリーム単位の一括取得が主要機能です。同時更新時の競合検出には、期待バージョン番号照合方式の楽観的排他制御を採用します。専用製品のEventStoreDB（現KurrentDB）や、PostgreSQLなど汎用RDBMS基盤の独自実装が代表例です。

### 集約（Aggregate）

ドメイン駆動設計（DDD）の集約概念と高相性です。コマンド受信時、集約は自身のイベント履歴を再生して現在状態を復元し、ビジネスルールの検証後に新規イベントを発行します。

### プロジェクション

イベント列から参照用データモデルを生成する処理です。画面表示や検索用途に最適化したリードモデルを、イベント購読経由で非同期に更新します。CQRS（コマンドクエリ責務分離）との併用が一般的です。

```typescript
type AccountEvent =
  | { type: "AccountOpened"; accountId: string }
  | { type: "Deposited"; amount: number }
  | { type: "Withdrawn"; amount: number };

// 全イベントの順次適用で現在残額を算出
function replay(events: AccountEvent[]): number {
  return events.reduce((balance, e) => {
    switch (e.type) {
      case "Deposited": return balance + e.amount;
      case "Withdrawn": return balance - e.amount;
      default: return balance;
    }
  }, 0);
}
```

## 4. 導入メリット

**完全な監査証跡**：全状態変化が記録対象なので、監査ログの別途実装は不要です。金融・医療など規制業界との親和性も良好です。

**時点復元（タイムトラベル）**：任意時点までのイベント再生で、過去状態を正確に再現可能です。障害調査や不具合再現の際に強力な武器です。

**リードモデルの柔軟な追加**：新規要件の発生時も、既存イベントの再処理で新規プロジェクションを事後的に構築可能です。

**ドメイン理解の深化**：イベント名称がビジネス領域の事象と直結するので、ドメインエキスパートとの対話も円滑です。

**システム間連携**：イベントは外部システムへの通知メッセージとしても再利用可能です。

## 5. 課題と注意点

**イベントスキーマの進化**：過去イベントは変更禁止なので、構造変更時はバージョニング戦略が必須です。旧形式イベントの参照時に新形式へ変換する「アップキャスト」手法が代表的対策です。

**再生コストの増大**：イベント数の増加に比例して、状態復元の処理時間も増加します。一定間隔で集約状態を保存する「スナップショット」の併用で、再生対象を最新スナップショット以後のイベントに限定可能です。

**結果整合性**：プロジェクション更新は非同期処理が基本なので、コマンド処理直後の参照結果に最新内容が未反映のケースも発生します。UI設計段階での考慮が必要です。

**個人情報の削除要求**：GDPRなどの規制は個人データの削除を要求しますが、イベントは原則不変です。個人情報の暗号化と暗号キーの破棄で事実上の削除を実現する「クリプトシュレッディング」が代表的解決策です。

**学習コスト**：CRUD方式と比較して概念数が増加し、チーム全体の習熟に相応の時間を要します。

## 6. 適用判断の基準

イベントソーシングは汎用的な最適解とは異質の、特定条件下で真価を発揮する設計手法です。

**適合ケース**

- 監査・コンプライアンス要件が厳格なドメイン（金融、会計、医療）
- 状態遷移自体にビジネス価値が存在するドメイン（注文処理、在庫管理、ワークフロー）
- 過去データの多角的分析需要が旺盛なシステム
- 複数マイクロサービス間でイベント駆動連携を採用済みのシステム

**不適合ケース**

- 単純なマスタ管理など、履歴の価値が希薄なCRUD中心アプリケーション
- チーム内の関連知識が不足、かつ短期納品が最優先の案件
- 強整合性の即時参照が全面的に必須のシステム

導入時はシステム全体への一括適用を回避し、中核ドメインの特定バウンデッドコンテキスト限定で試験導入する方式が現実的です。イベントソーシングの本質は「事実の記録」と「状態の導出」の分離です。同原則の理解が、適切な設計判断の出発点です。
