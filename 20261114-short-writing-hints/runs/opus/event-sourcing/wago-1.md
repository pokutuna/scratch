# イベントソーシング入門:ソフトウェアエンジニア対象の技術解説

## 1. 概要と基本概念

イベントソーシング(Event Sourcing)は、アプリケーション状態の永続化方式の一種である。従来型の CRUD 設計では、データベース上に「最新状態」限定で保存し、更新処理の際に旧データを置換する。対照的に、イベントソーシングでは状態変化の原因である「イベント」を時系列順に追記保存し、現在状態はイベント列の再生処理で導出する。

具体例として銀行口座を想定する。CRUD 方式では、口座テーブルに「残額:7,000円」という単一レコードを保持する。イベントソーシング方式では、下記のイベント列を保存する。

| 連番 | イベント種別 | 金額 |
|---|---|---|
| 1 | 口座開設 | 0円 |
| 2 | 入金 | 10,000円 |
| 3 | 出金 | 3,000円 |

残額 7,000 円は保存対象ではなく、イベント列からの計算結果である。換言すると、イベントこそ唯一の「真実の源泉(Single Source of Truth)」であり、状態はイベントの派生物である。

## 2. 主要コンポーネントと処理フロー

イベントソーシングの主要コンポーネントは下記の通りである。

- **イベント**:過去時点で発生した事実の記録。命名は「OrderPlaced(注文確定済)」等、過去形が原則である。発生済の事実である以上、イベントは不変(イミュータブル)であり、更新・削除は原則禁止である。
- **イベントストア**:イベント専用の永続化層。追記専用(アペンドオンリー)のログ構造が基本で、集約単位のストリームとバージョン番号を管理する。EventStoreDB 等の専用製品以外に、PostgreSQL 等の RDB や Kafka の転用事例も存在する。
- **集約(アグリゲート)**:ドメイン駆動設計(DDD)由来の概念で、整合性境界の単位。コマンド受信時に過去イベントを再生して現在状態を復元し、ビジネスルール検証後に新規イベントを生成する。
- **コマンド**:状態変更の要求。「注文確定要求」等、命令形の意図表現であり、検証結果次第で拒否も発生する。
- **プロジェクション**:イベント列から参照用データ(リードモデル)を構築する処理。画面表示や検索の用途に最適化したビューを生成する。

全体の処理フローは「コマンド受信 → 集約のイベント再生と状態復元 → ビジネスルール検証 → 新規イベント追記 → プロジェクション更新」という順序である。

## 3. 利点

**完全な監査証跡**:全変更履歴が自動的に保存され、変更主体・変更日時・変更内容の追跡が容易である。金融・医療・会計等、監査要件の厳格な領域で特に有効である。

**タイムトラベル**:任意時点までのイベント再生により、過去状態の再現が可能である。障害調査、バグ再現、「先月末時点の在庫数」等の過去時点クエリに有用である。

**リードモデルの柔軟性**:新規要件の発生時、既存イベントから新規プロジェクションを事後構築可能である。データ分析用途のビュー追加も、本番のコマンド側への影響は皆無である。

**CQRS との親和性**:CQRS(コマンドクエリ責務分離)はコマンド側とクエリ側のモデル分離を提唱するアーキテクチャパターンであり、イベントソーシングとの併用が一般的である。コマンド側はイベント追記に専念し、クエリ側は用途別に最適化したリードモデルを提供する。

**ドメイン理解の促進**:イベント名称がビジネス上の事象と直結し、ドメインエキスパートとの対話を通じたユビキタス言語の確立が容易である。

## 4. 課題と注意点

**学習コストと複雑性**:CRUD と比較して概念数が多数であり、チーム全体の理解が必要である。単純な業務アプリケーションへの適用は過剰設計の危険性大である。

**結果整合性**:プロジェクション更新は非同期処理が一般的であり、更新直後の参照結果に旧データが残存する現象が発生する。UI 設計上の配慮が必須である。

**イベントスキーマの進化**:イベントは不変であり、過去イベントの改変は原則不可である。スキーマ変更の際は、バージョン付与、アップキャスト(デシリアライズ時の旧形式から新形式への変換)、寛容なデシリアライズ等の戦略が必要である。

**再生コストの増大**:イベント数の増加に比例して状態復元処理が高負荷化する。対策として、スナップショット(特定時点の状態)を定期作成し、スナップショット以後のイベントに限定して再生する手法が一般的である。

**個人情報と削除要件**:GDPR 等の削除権(第17条)と不変ログの原則は衝突する。対策として、クリプトシュレッディング(個人単位の暗号鍵の破棄による実質的消去)や、個人情報の外部ストアへの分離保管が存在する。

## 5. 導入判断と実装指針

**適合領域**

- 監査・コンプライアンス要件の厳格なシステム
- 状態遷移自体に業務的価値が存在するドメイン(注文管理、在庫管理、ワークフロー等)
- 複数のリードモデルや分析基盤への展開需要が大規模なシステム

**不適合領域**

- 単純なマスタ管理・設定管理
- 履歴情報の業務的価値が低位のシステム
- チームの分散システム運用経験が不足した状況

**実装指針**

1. **全面採用の回避**:システム全体ではなく、バウンデッドコンテキスト単位での部分採用を推奨する。
2. **イベント設計の重視**:「StatusChanged」等の汎用イベントではなく、業務的意味の明確なイベント名称を採用する。
3. **楽観的排他制御**:追記時に期待バージョンを指定し、並行更新の競合を検出する。
4. **冪等性の確保**:プロジェクションや外部連携は重複配信を前提とし、冪等処理を実装する。
5. **既存フレームワークの活用**:Axon Framework、Marten、EventStoreDB 等の活用により、基盤実装の負担を軽減する。

## 6. 総括

イベントソーシングは「状態」ではなく「変化の事実」を一次データとする設計パラダイムである。監査性・再現性・拡張性の獲得の代償として、複雑性・結果整合性・スキーマ進化という課題が発生する。万能の解決策ではなく、ドメイン特性とチーム能力を考慮した選択的適用こそ、導入成功の要諦である。
