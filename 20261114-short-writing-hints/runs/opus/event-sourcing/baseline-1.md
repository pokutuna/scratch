# イベントソーシング入門：状態ではなく「出来事」を記録する設計

## 1. イベントソーシングとは何か

多くのアプリケーションは、データベースに「現在の状態」を保存します。たとえば銀行口座なら `accounts` テーブルに `balance = 12000` という行があり、入金や出金のたびに `UPDATE` で上書きします。この方式は直感的ですが、上書きされた過去の値は失われます。「なぜ残高が 12000 円になったのか」を知るには、別途ログや履歴テーブルを用意しなければなりません。

**イベントソーシング（Event Sourcing）** は、状態そのものではなく、**状態を変化させた出来事（イベント）の列**を唯一の信頼できる情報源（Source of Truth）として保存する設計パターンです。口座であれば次のように記録します。

1. `AccountOpened`（口座開設）
2. `MoneyDeposited { amount: 20000 }`
3. `MoneyWithdrawn { amount: 8000 }`

現在の残高は、これらのイベントを先頭から順に適用（リプレイ）すると求まります。会計の世界の「仕訳帳」と同じ考え方です。帳簿は消しゴムで書き換えず、訂正が必要なら「取消仕訳」を追記します。イベントソーシングも同様に、過去のイベントは不変（immutable）で、変更は常に新しいイベントの追記として表現します。

## 2. 基本的な構成要素と仕組み

イベントソーシングを構成する主な要素は次のとおりです。

- **イベント**：過去に起きた事実を表すデータ。名前は過去形（`OrderPlaced`、`ItemShipped`）にするのが慣例です。「何をしたいか」ではなく「何が起きたか」を記録します。
- **イベントストア**：イベントを追記専用（append-only）で保存するストレージ。EventStoreDB のような専用製品のほか、RDB のテーブルや Kafka などで実装されることもあります。
- **集約（Aggregate）**：整合性を保つ単位となるエンティティ。イベントは集約 ID ごとのストリームとして保存されます。
- **リハイドレーション**：ストリームのイベントを順に適用し、集約の現在状態を復元する処理。

TypeScript で簡単に書くと、次のようなイメージです。

```typescript
type Event =
  | { type: "AccountOpened"; accountId: string }
  | { type: "MoneyDeposited"; amount: number }
  | { type: "MoneyWithdrawn"; amount: number };

type Account = { balance: number };

function apply(state: Account, event: Event): Account {
  switch (event.type) {
    case "AccountOpened":  return { balance: 0 };
    case "MoneyDeposited": return { balance: state.balance + event.amount };
    case "MoneyWithdrawn": return { balance: state.balance - event.amount };
  }
}

const rehydrate = (events: Event[]) =>
  events.reduce(apply, { balance: 0 });
```

コマンド（例：「8000 円出金せよ」）を処理するときは、まず集約を復元し、ビジネスルール（残高不足でないか）を検証してから、新しいイベントを生成して追記します。状態の計算は `reduce` という純粋関数なので、テストしやすいのも特徴です。

イベント数が膨大になるとリプレイが遅くなるため、ある時点の状態を保存しておく**スナップショット**を併用するのが一般的です。復元時はスナップショットを読み込み、それ以降のイベントだけを適用します。

## 3. 得られるメリット

**完全な監査ログ**：すべての変更が理由付きで残るため、「いつ、誰が、何をしたか」を後から正確に追跡できます。金融や医療など、監査要件が厳しい領域と相性が良いです。

**過去の任意時点の状態を再現できる**：特定日時までのイベントだけをリプレイすれば、その時点の状態が得られます。「先月末時点の在庫数は？」といった時間軸のある問い合わせや、本番障害の再現・デバッグに役立ちます。

**読み取りモデルを後から自由に作れる**：イベントという生の事実が残っているので、新しい集計画面や分析用テーブルが必要になったとき、過去のイベントを流し直してゼロから構築できます。状態だけを保存していると、捨てた情報は二度と取り戻せません。

**他システムとの連携が自然**：イベントはそのままドメインイベントとして外部へ発行でき、マイクロサービス間の非同期連携の基盤になります。

## 4. 難しさと注意点

メリットの裏側には、無視できないコストがあります。

**イベントスキーマの進化**：イベントは不変で永続的に残るため、構造を変えたくなっても過去のデータは書き換えられません。古い形式のイベントを読み込み時に新形式へ変換する**アップキャスティング**や、バージョン付きのイベント型を用意するなどの戦略が必要です。設計初期にイベントの粒度や命名をよく検討することが重要です。

**クエリが難しい**：「残高 10 万円以上の口座一覧」のような横断検索は、イベントストアに対して直接行えません。後述する読み取りモデルを別途構築する必要があります。

**結果整合性**：読み取りモデルはイベントを非同期で反映するため、書き込み直後の画面に最新状態がまだ出ないことがあります。UI 設計やユーザーへの説明で吸収しなければなりません。

**並行更新の制御**：同じ集約に同時に書き込むと矛盾が生じ得ます。追記時に「期待するバージョン番号」を指定し、一致しなければ失敗させる楽観的ロックで対処するのが定石です。

**個人情報の削除**：GDPR などの「忘れられる権利」は、不変のイベントと衝突します。個人データをユーザーごとの鍵で暗号化し、削除時は鍵を破棄する**クリプトシュレッディング**などの工夫が求められます。

**学習コスト**：チーム全員が CRUD とは異なる思考法に慣れる必要があり、運用・デバッグのツールも整えなければなりません。

## 5. CQRS との組み合わせと導入判断

イベントソーシングは、**CQRS（Command Query Responsibility Segregation）** と組み合わせて使われることがほとんどです。CQRS は書き込み（コマンド）と読み取り（クエリ）のモデルを分離する考え方で、イベントストアを書き込み側、イベントから生成した非正規化テーブルや検索インデックスを読み取り側とします。イベントを購読して読み取りモデルを更新する処理は**プロジェクション**と呼ばれます。これにより、前節の「クエリが難しい」という弱点を補えます。

では、どんなときに採用すべきでしょうか。目安は次のとおりです。

- **向いている**：監査や履歴が業務上の価値を持つ（会計、決済、在庫、予約）、ドメインが複雑で「何が起きたか」の表現が重要、イベント駆動のシステム連携が前提になっている。
- **向いていない**：単純なマスタ管理や CRUD 中心のアプリ、チームに経験がなく納期が厳しい、履歴に業務的な意味が薄い。

重要なのは、システム全体に一律で適用する必要はないという点です。ドメイン駆動設計の境界づけられたコンテキストごとに判断し、価値の高い中核部分にだけ導入するのが現実的です。

イベントソーシングは「データを上書きせず、事実を積み重ねる」というシンプルな発想から、強力な追跡性と柔軟性をもたらします。その一方で、スキーマ進化や結果整合性といった固有の課題も伴います。トレードオフを理解したうえで、適所に使うことが成功の鍵です。
