# イベントソーシング入門

## 1. イベントソーシングとは

イベントソーシング（Event Sourcing）は、アプリケーションの状態を「現在の値」として保存しない設計手法です。代わりに、状態を変化させた出来事（イベント）の列を保存します。現在の状態は、イベントを先頭から順に適用し直して導き出します。

一般的な CRUD 型の設計では、銀行口座の残高を `balance = 7000` のようにテーブルの 1 行で持ち、入出金のたびに上書きします。上書きした時点で「なぜその値になったのか」という情報は失われます。イベントソーシングでは、代わりに次のような記録を残します。

```
1. AccountOpened   { accountId: "A-1" }
2. MoneyDeposited  { amount: 10000 }
3. MoneyWithdrawn  { amount: 5000 }
4. MoneyDeposited  { amount: 2000 }
```

残高 7000 は、これらを順に畳み込んだ結果にすぎません。会計の仕訳帳、Git のコミット履歴、データベースの WAL（先行書き込みログ）と同じ発想です。核心は「事実の記録が正であり、現在の状態はそこから計算される派生物である」という考え方にあります。

## 2. 基本的な構成要素

### イベント

イベントは、ドメイン上で起きた事実を表すオブジェクトです。`OrderPlaced` や `ItemShipped` のように、過去形で命名するのが慣例です。すでに起きた事実なので、一度記録したイベントは変更も削除もしない「追記専用（append-only）」として扱います。誤りがあった場合も元のイベントは書き換えません。打ち消すための新しいイベント（`DepositCorrected` など）を追加します。

### イベントストア

イベントを永続化する専用のストレージです。最低限の要件は、集約ごとのストリームにイベントを順序付きで追記し、ストリーム単位で読み出せることです。EventStoreDB のような専用製品のほか、RDB のテーブルや Kafka で実装されることもあります。

### 集約と状態の再構築

システムがコマンド（「出金せよ」などの要求）を受け取ると、次の流れで処理します。

1. 対象の集約に属するイベントをすべて読み込み、状態を再構築する
2. その状態に対して、残高不足でないかといったビジネスルールを検証する
3. 問題がなければ新しいイベントを生成し、ストアに追記する

擬似コードで書くと次のようになります。

```typescript
function handleWithdraw(cmd: Withdraw) {
  const events = store.load(cmd.accountId);
  const state = events.reduce(apply, initialState);
  if (state.balance < cmd.amount) throw new InsufficientFunds();
  store.append(cmd.accountId,
    [{ type: "MoneyWithdrawn", amount: cmd.amount }],
    /* expectedVersion */ events.length);
}
```

`expectedVersion` は楽観的排他制御のための値です。読み込んだ後に別のイベントが追記されていた場合は書き込みを失敗させ、競合を検出します。

## 3. プロジェクションと CQRS

イベント列は、そのままでは検索や一覧表示に向きません。たとえば「残高が 10 万円以上の口座一覧」を問い合わせるたびに全イベントを再生するのは非現実的です。

そこで、イベントを購読して読み取り用に最適化されたデータ（リードモデル）を作ります。この仕組みをプロジェクションと呼びます。リードモデルは RDB のテーブルでも、検索エンジンのインデックスでも、キャッシュでも構いません。用途ごとに複数作れる点が利点です。

このように書き込み側（コマンド）と読み取り側（クエリ）のモデルを分離する設計を、CQRS（Command Query Responsibility Segregation）と呼びます。イベントソーシングとセットで採用されることが多いものの、両者は独立した概念です。CQRS だけを採用することもできます。

プロジェクションは通常非同期に更新されるため、書き込み直後の読み取りには結果がまだ反映されていないことがあります。この「結果整合性」を前提にした設計が必要です。

## 4. メリット

- **完全な監査ログ**: すべての変更が事実として残るため、「いつ・誰が・何をしたか」を後から追跡できます。金融や医療など、監査要件の厳しい領域と相性が良い手法です。
- **時間を遡った分析**: 任意の時点までイベントを再生すれば、その時点の状態を再現できます。障害調査やバグの再現にも役立ちます。
- **リードモデルの後付け**: 新しい集計や画面が必要になったら、過去のイベントを最初から再生して新しいプロジェクションを構築できます。CRUD では捨てていた情報が資産になります。
- **ドメインの表現力**: システムが `UPDATE` ではなく「注文がキャンセルされた」といった業務上の言葉で記述されます。そのため、ドメイン駆動設計（DDD）と組み合わせやすくなります。
- **他システムとの連携**: イベントをそのまま外部へ発行すれば、マイクロサービス間の連携や非同期処理の起点として使えます。

## 5. 難しさと注意点

一方で、導入コストは小さくありません。

- **イベントスキーマの進化**: イベントは不変なので、古い形式のイベントも永遠に読み続ける必要があります。フィールドの追加や名前変更のたびに、読み込み時に新形式へ変換する「アップキャスト」などの仕組みが要ります。イベントの粒度や命名は後から直しにくいため、最初の設計に慎重さが求められます。
- **再構築の性能**: イベント数が多い集約では、毎回全件を再生すると遅くなります。一定間隔で状態を保存するスナップショットで緩和できますが、管理すべき仕組みが一つ増えます。
- **結果整合性**: リードモデルは遅れて更新されます。ユーザーへの見せ方を含め、UI 設計での工夫が必要です。
- **削除の扱い**: 追記専用という性質は、GDPR などが求める個人データの削除と衝突します。対策として、個人情報を暗号化して保存し、鍵を破棄して実質的に消去する「クリプトシュレッディング」などを検討します。
- **学習コストと運用**: チームにとって馴染みのない概念が多く、デバッグや運用の手順も CRUD とは異なります。アドホックな SQL で状態を直接書き換えるような対処もできません。

## 6. 導入判断の指針

イベントソーシングは強力ですが、すべてのシステムに向くわけではありません。次のような場合は検討する価値があります。

- 変更履歴そのものに業務上の価値がある（会計、在庫、予約、ワークフローなど）
- 監査や規制の要件で、完全な履歴が求められる
- 同じデータを多様な観点で集計・表示したい
- 複雑なドメインロジックを持ち、DDD を実践している

逆に、単純なマスタ管理や、履歴に価値がない CRUD 中心の画面に導入しても、複雑さに見合う利益は得られません。適用範囲もシステム全体ではなく、コアとなる一部の境界づけられたコンテキストに絞るのが現実的です。

まずは小さな集約で試してみるのがおすすめです。イベントの設計、プロジェクションの運用、スキーマ進化の扱いを経験してから範囲を広げましょう。「状態ではなく事実を記録する」という視点は、全面的に採用しない場合でも、ログや監査テーブルの設計に活かせます。
