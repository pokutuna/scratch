# イベントソーシング入門

## 1. イベントソーシングとは

イベントソーシング（Event Sourcing）は、アプリケーションの状態を「現在の値」ではなく、**状態を変化させた出来事（イベント）の列**として永続化する設計パターンです。

一般的な CRUD 型のシステムでは、銀行口座の残高が 10,000 円なら、データベースには `balance = 10000` という最新値だけが保存されます。どのような経緯でその値になったのかは、別途ログを残さない限り失われます。

イベントソーシングでは、次のような事実の記録を保存します。

```
AccountOpened    { accountId: "A-1" }
MoneyDeposited   { amount: 15000 }
MoneyWithdrawn   { amount: 3000 }
MoneyWithdrawn   { amount: 2000 }
```

現在の残高 10,000 円は、これらのイベントを先頭から順に適用して**導出される値**です。イベントこそが唯一の信頼できる情報源（Single Source of Truth）であり、現在の状態はその計算結果にすぎない、というのが中心的な考え方です。

会計の仕訳帳や Git のコミット履歴を思い浮かべると理解しやすいでしょう。どちらも「変更の記録」を積み重ね、そこから現在の姿を再構成しています。

## 2. 基本的な仕組み

### イベントストア

イベントは**追記専用（append-only）**のストアに保存します。一度書き込んだイベントは更新も削除もしません。誤りがあった場合も、過去を書き換えるのではなく「訂正イベント」を新たに追加します。

イベントは通常、集約（Aggregate）と呼ばれる一貫性の単位ごとのストリームにまとめられます。各イベントにはストリーム内の連番（バージョン）が振られます。

### 状態の復元

集約の現在の状態は、イベント列を畳み込む（fold する）ことで得られます。

```typescript
type Event =
  | { type: "MoneyDeposited"; amount: number }
  | { type: "MoneyWithdrawn"; amount: number };

type Account = { balance: number };

function apply(state: Account, event: Event): Account {
  switch (event.type) {
    case "MoneyDeposited":
      return { balance: state.balance + event.amount };
    case "MoneyWithdrawn":
      return { balance: state.balance - event.amount };
  }
}

const rehydrate = (events: Event[]) =>
  events.reduce(apply, { balance: 0 });
```

### コマンド処理の流れ

書き込みは典型的に次の手順で行います。

1. ストリームからイベントを読み込み、集約の状態を復元する
2. コマンド（例：「3,000 円引き出す」）を受け取り、残高不足などのビジネスルールを検証する
3. 検証に通れば新しいイベントを生成し、ストアに追記する

このとき、読み込んだバージョンを期待値として追記する**楽観的排他制御**を用いるのが一般的です。並行して別のイベントが書き込まれていれば追記は失敗し、再試行します。

## 3. 得られるメリット

**完全な監査証跡**
すべての変更が業務上の意味を持つイベントとして残るため、「誰が・いつ・なぜ」を後から追跡できます。金融や医療など、説明責任が求められる領域で特に有効です。

**任意時点の状態再現**
特定の時刻までのイベントだけを適用すれば、過去のある時点の状態を再現できます。「先月末時点の在庫はいくつだったか」という問いに、追加の仕組みなしで答えられます。

**デバッグと障害解析**
本番で起きた不具合も、該当ストリームのイベントを手元で再生すれば再現できます。状態がどのような経緯で壊れたのかを一歩ずつ追えるのは大きな利点です。

**読み取りモデルの柔軟な追加**
イベントを購読して、用途別の読み取り専用ビュー（プロジェクション）を作れます。後から「月別の売上集計」が必要になっても、既存のイベントを最初から再生すれば新しいビューを構築できます。このため CQRS（コマンドとクエリの責務分離）と組み合わせて使われることが多いです。

**システム間連携との親和性**
イベントはそのまま他サービスへの通知として利用でき、イベント駆動アーキテクチャと自然に統合できます。

## 4. 注意点と難しさ

### イベントスキーマの進化

イベントは不変で、長期間保存されます。そのため、イベントの構造を変更したくなったとき、過去のイベントとの互換性を保つ必要があります。代表的な対処法は次のとおりです。

- フィールドの追加は後方互換に留め、既存フィールドの意味を変えない
- 読み込み時に古い形式を新しい形式へ変換する**アップキャスト**を実装する
- 意味が大きく変わる場合は、別の型として新しいイベントを定義する

### パフォーマンスとスナップショット

イベント数が増えると、毎回すべてを再生するコストが無視できなくなります。一定間隔で状態を保存する**スナップショット**を導入し、そこから先のイベントだけを適用することで対処します。ただし、スナップショットはあくまで最適化であり、真実の源はイベントであることを忘れないようにします。

### 結果整合性

プロジェクションは非同期で更新されることが多く、書き込み直後の読み取りに最新の結果が反映されていない場合があります。UI 設計やユーザーへの見せ方で、この遅延を前提にした工夫が必要です。

### データ削除の要件

追記専用という性質は、個人情報の削除要求（GDPR の「忘れられる権利」など）と衝突します。個人情報をイベント外に保管して参照のみ持たせる方法や、ユーザーごとの鍵で暗号化し、削除時に鍵を破棄する**クリプトシュレッディング**などの手法が用いられます。

### イベント設計の難しさ

`AccountUpdated` のような汎用的なイベントは、単なる変更差分のログになり、イベントソーシングの価値を損ないます。`AddressChanged` や `CreditLimitRaised` のように、**ドメインで実際に起きた出来事を過去形で表す**名前と粒度を選ぶことが重要です。ドメインエキスパートとの対話が欠かせません。

## 5. 導入を判断する基準

イベントソーシングは強力ですが、学習コストと運用の複雑さを伴います。システム全体に一律で適用するのではなく、価値が見込める部分に限定して採用するのが現実的です。

**向いているケース**

- 変更履歴そのものに業務上の価値がある（会計、決済、在庫、予約など）
- 監査や規制対応で、変更経緯の説明が求められる
- 同じデータに対して多様な読み取りビューが必要になる
- ドメインが複雑で、状態遷移をビジネス上の出来事として表現したい

**向いていないケース**

- 単純なマスタ管理など、CRUD で十分に表現できる
- 履歴にほとんど価値がなく、最新値だけ分かればよい
- チームにドメイン駆動設計や非同期処理の経験が乏しく、学習の余裕もない

迷った場合は、まず中核となる 1 つの境界づけられたコンテキストで試し、スキーマ進化や運用の手触りを確かめてから適用範囲を広げることをお勧めします。

イベントソーシングの本質は「何が起きたか」を第一級の情報として扱うことにあります。この視点を持つだけでも、CRUD 中心の設計では見落としがちなドメインの振る舞いに気づけるはずです。
