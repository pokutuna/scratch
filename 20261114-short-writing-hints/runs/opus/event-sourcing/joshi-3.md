# イベントソーシング入門

## 1. イベントソーシングとは

イベントソーシング（Event Sourcing）は、アプリケーションの状態を「現在の値」ではなく「状態を変化させた出来事の列」として記録する設計手法である。一般的な CRUD 型のシステムでは、テーブルの行を UPDATE し、最新の状態だけを保持する。これに対してイベントソーシングでは、「注文が作成された」「商品が追加された」「支払いが完了した」といった出来事（イベント）を追記専用のストアに保存する。現在の状態は、それらのイベントを先頭から順に適用して導き出す。

銀行口座の通帳を思い浮かべると理解しやすい。通帳には残高だけでなく、入金と出金の履歴が並んでいる。残高は、その履歴を合計した結果にすぎない。イベントソーシングは、この考え方をアプリケーションのデータモデル全体に適用したものといえる。

## 2. 基本的な構成要素

イベントソーシングは、主に次の 4 つの要素で構成される。

- **イベント**: ドメインで起きた事実を表す不変のレコード。`OrderPlaced` や `ItemAdded` のように、過去形で命名するのが慣例である。いったん記録したイベントは、変更も削除もしない。
- **イベントストア**: イベントを追記専用で永続化する場所。集約ごとのストリームに分けて保存し、ストリーム内の順序を保証する。
- **集約（Aggregate）**: 整合性を保つ単位となるドメインオブジェクト。コマンドを受け取ると、ビジネスルールを検証したうえで新しいイベントを発行する。
- **プロジェクション**: イベントを購読し、検索や画面表示に適した読み取りモデルを組み立てる処理。

状態の復元は、ストリーム内のイベントを順に畳み込む（fold する）処理として表現できる。

```typescript
type Event =
  | { type: "AccountOpened"; owner: string }
  | { type: "Deposited"; amount: number }
  | { type: "Withdrawn"; amount: number };

type Account = { owner: string; balance: number };

function apply(state: Account, event: Event): Account {
  switch (event.type) {
    case "AccountOpened":
      return { owner: event.owner, balance: 0 };
    case "Deposited":
      return { ...state, balance: state.balance + event.amount };
    case "Withdrawn":
      return { ...state, balance: state.balance - event.amount };
  }
}

const rehydrate = (events: Event[]): Account =>
  events.reduce(apply, { owner: "", balance: 0 });
```

コマンドは「現在の状態を復元する」「ルールを検証する」「新しいイベントを追記する」という 3 段階で処理する。たとえば出金コマンドであれば、残高が不足していないことを確認してから `Withdrawn` イベントを追記する。

## 3. 得られる利点

最大の利点は、変更の履歴が完全に残ることである。監査ログを別途作り込まなくても、いつ、誰が、何をしたかがイベントとして記録される。そのため、金融や医療のように説明責任が求められる領域とは特に相性がよい。

次に、過去の任意の時点の状態を再現できる。障害調査の際は、問題が起きた時刻までのイベントだけを適用すれば、当時の状態を手元で再現できる。

さらに、読み取りモデルを後から追加できる点も見逃せない。新しい分析要件が生まれたら、新しいプロジェクションを実装し、既存のイベントを最初から流し直せばよい。データの持ち方を事前にすべて決めておく必要がないので、要件の変化に強い。

加えて、イベントは他のサービスへの通知としてもそのまま利用できる。マイクロサービス間の連携やイベント駆動アーキテクチャと親和性が高いのは、このためである。

## 4. 注意すべき課題

一方で、イベントソーシングは導入の負担が小さくない手法でもある。

**結果整合性**: 書き込み側のイベントストアと読み取りモデルは、非同期に更新されることが多い。その結果、書き込んだ直後の画面に変更が反映されていない状況が起こりうる。この遅延は、UI の設計段階から考慮しておく必要がある。

**イベントスキーマの進化**: イベントは不変なので、過去のイベントの形式を書き換えることはできない。フィールドの追加や意味の変更が生じた場合は、イベントにバージョン番号を付与し、読み込み時に新しい形式へ変換する仕組み（アップキャスト）を用意する。

**復元コストの増大**: イベントが増えるにつれて、状態の復元に時間がかかるようになる。一般的な対策は、一定間隔で状態のスナップショットを保存し、そこから差分のイベントだけを適用する方法である。

**削除要求への対応**: GDPR などの規制で個人データの削除を求められても、追記専用のストアからは単純に消せない。対策としては、個人データを暗号化して保存し、削除時に鍵を破棄する「暗号シュレッディング」がよく使われる。

**学習コスト**: チーム全員が、CRUD とは異なる考え方に慣れる必要がある。また、イベントの粒度や命名を誤ると、後から修正するのは難しい。

## 5. 導入を判断するために

イベントソーシングは、すべてのシステムに向く手法ではない。単純なマスタ管理や、履歴に業務上の価値がない領域に適用しても、複雑さが増すだけで得るものは少ない。

導入を検討する価値があるのは、たとえば次のような場合である。

- 状態の変化そのものに業務上の意味があり、履歴を追跡したい
- 監査や規制への対応として、変更の証跡が求められる
- 同じデータを多様な観点から参照するため、読み取りモデルを柔軟に増やしたい

なお、システム全体に一律で適用する必要はない。注文や決済のように履歴が重要な境界づけられたコンテキストにだけ導入し、それ以外は従来どおり CRUD で実装する、という使い分けが現実的である。CQRS（コマンドとクエリの責務分離）と組み合わせることが多いが、両者は独立した概念であり、片方だけを採用することもできる。

まずは小さな領域で試し、イベント設計やスキーマ進化の運用を経験してから、適用範囲を広げていくとよい。

**助詞・助動詞・接続詞について見直した点**

- **文体の統一**: 「だ」と「である」が混在しないよう、文末を「である」調にそろえました。
- **「が」の重複**: 1 文の中で主格の「が」が重なる箇所や、逆接の「が」で文を長くつないでいる箇所を、文の分割や言い換えで解消しました。
- **「の」の連続**: 「〜の〜の〜」と続く箇所を「〜における」「〜内の」などに言い換えて減らしました。
- **接続詞の使い分け**: 利点の列挙は「次に」「さらに」「加えて」と段階的に並べ、論点の転換には「一方で」、補足には「なお」を使いました。「また」と「そして」の多用は避けています。
- **因果の表現**: 「ため」「ので」「その結果」を文脈に応じて使い分け、同じ表現が続かないようにしました。
