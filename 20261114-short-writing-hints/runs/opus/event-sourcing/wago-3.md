# イベントソーシング解説

## 1. 概要と基本概念

イベントソーシング（Event Sourcing）は、アプリケーションの状態を「現在値」として保存する方式ではない。状態変化の原因である事象（イベント）を時系列順に記録し、当該イベント列の累積から状態を導出する設計手法である。

一般的なシステムでは、データベースの各レコードが最新状態のみを保持し、更新の都度、以前の値は消失する。イベントソーシングでは逆に、「口座開設」「入金」「出金」等の業務上の事実を不変のレコードとして追記専用ストアに保存する。現在の残額は、全イベントを先頭から順次適用する処理（リプレイ）で算出する。

類似の概念として、会計帳簿や Git のコミット履歴が存在する。会計の世界では、誤記の訂正にも過去記録の消去は不可であり、訂正用の記帳を追加する。Git もコミット履歴の連鎖でリポジトリの変遷を表現する。イベントソーシングは、同様の発想をアプリケーションのドメインデータに適用する手法と解釈可能である。

イベントの命名には過去形の動詞を使用する（`OrderPlaced`、`PaymentCompleted` 等）。イベントは「発生済みの確定事実」であり、事後の改変・削除は原則禁止である。

## 2. 従来型 CRUD との比較

| 観点 | CRUD 型 | イベントソーシング |
|---|---|---|
| 保存対象 | 現在状態 | 状態変化の履歴 |
| 更新操作 | UPDATE / DELETE による改変 | 追記（Append）専用 |
| 履歴情報 | 原則消失（別途監査ログが必要） | 全件保存 |
| 参照処理 | 単純・高速 | プロジェクション設計に依存 |
| スキーマ変更 | マイグレーションで一括変換 | 過去イベントとの互換性維持が必須 |

CRUD 型は現在状態の把握が容易な反面、状態到達の経緯に関する情報が欠落する。具体例として、EC サイトの注文テーブルに `status = 'cancelled'` のレコードが存在する際を想定する。顧客都合のキャンセルか、在庫不足による自動キャンセルかは、別途ログ設計が未実施の状態では判別不可能である。

イベントソーシングでは `OrderPlaced` → `StockShortageDetected` → `OrderCancelled` の一連のイベント自体が記録対象であり、経緯の追跡が自動的に実現する。

## 3. 主要な構成要素

### イベントストア

イベントを追記専用で永続化するデータストアである。各イベントは、ストリーム ID（集約単位の識別子）、バージョン番号、イベント種別、ペイロード、発生時刻等の属性を保持する。専用製品として EventStoreDB が有名であるが、PostgreSQL 等の RDB での実装も一般的である。

### 集約（Aggregate）

ドメイン駆動設計（DDD）の集約が、イベントストリームの単位に相当する。コマンド処理の標準フローは下記である。

1. コマンド（`Withdraw` 等）を受信
2. 対象集約の過去イベントをリプレイし、現在状態を復元
3. ビジネスルールを検証（残額不足の検出等）
4. 検証成功の際、新規イベント（`Withdrawn`）を生成
5. 期待バージョン番号を指定してイベントストアに追記（楽観的排他制御）

状態復元処理は、典型的には fold / reduce 演算として実装する。

```ts
type AccountEvent =
  | { type: "AccountOpened" }
  | { type: "Deposited"; amount: number }
  | { type: "Withdrawn"; amount: number };

function apply(balance: number, e: AccountEvent): number {
  switch (e.type) {
    case "AccountOpened": return 0;
    case "Deposited":     return balance + e.amount;
    case "Withdrawn":     return balance - e.amount;
  }
}

const balance = events.reduce(apply, 0); // 現在残額
```

### プロジェクションとリードモデル

イベント列は検索・集計に不適であり、参照用途には別途「リードモデル」を構築する。イベントを購読して参照用テーブルを更新する処理をプロジェクションと称する。ライト側（コマンド）とリード側（クエリ）のモデル分離は CQRS（Command Query Responsibility Segregation）と称し、イベントソーシングとの併用が一般的である。

### スナップショット

イベント件数が膨大な集約では、毎回の全件リプレイが高負荷化する。一定件数単位で状態のスナップショットを保存し、復元時には最新スナップショット以降のイベントのみを適用する最適化手法が存在する。

## 4. 利点

- **完全な監査証跡**：全変更が変更理由を含めて記録され、金融・医療等の監査要件への対応が容易である。
- **任意時点の状態復元**：特定時刻までのイベントのみをリプレイすれば、過去状態の再現が可能である。障害調査やデバッグで特に有効である。
- **事後的な分析・機能追加**：新規要件の発生時、過去の全イベントから新規プロジェクションを構築可能である。CRUD 型では消失済みの情報も、イベントとして保存済みであり活用可能である。
- **システム間の疎結合**：イベント駆動アーキテクチャとの親和性が良好であり、マイクロサービス間連携を疎結合に設計可能である。
- **ライト処理の単純化**：追記操作のみでロック競合が局所化し、ライト性能の確保が容易である。

## 5. 課題と注意点

- **結果整合性**：プロジェクション更新は非同期処理が一般的である。コマンド実行直後のリードモデルに最新状態が未反映の可能性が存在し、UI 設計段階での考慮が必要である。
- **イベントスキーマの進化**：保存済みイベントは改変不可であり、スキーマ変更時は旧形式との互換性維持が必須である。イベント種別のバージョニングや、リプレイ時に旧形式を新形式へ変換するアップキャスティングの導入が一般的である。
- **個人情報の削除要求**：GDPR 等の法規制による削除要求と「不変の履歴」は原理的に衝突する。個人情報をユーザー単位の暗号化キーで暗号化し、削除要求時にキーを破棄する「クリプトシュレッディング」が代表的な対策である。
- **設計難易度**：イベント粒度の決定は困難である。粒度過大では意図が不明確化し、粒度過小では件数が爆発的に増大する。チーム全体の学習コストも無視不可能な水準である。
- **アドホックな検索の困難性**：「特定条件の全顧客」等の横断検索は、対応するプロジェクションが未構築の状態では実行困難である。

## 6. 導入判断の指針

イベントソーシングは強力な反面、全システムへの一律適用は推奨不可である。下記の観点で適合性を判断する。

**適合ケース**

- 監査証跡や変更履歴自体が業務価値を保有する領域（会計、決済、在庫、物流等）
- 業務プロセスが複雑で、状態遷移の経緯がドメイン知識として重要な領域
- 将来的な多様な分析需要が想定される領域

**不適合ケース**

- 単純なマスタ管理や設定情報等、現在値のみで十分な領域
- チームに CQRS・DDD の経験が皆無で、短期間での開発完了が最優先のプロジェクト

実務上は、システム全体ではなくバウンデッドコンテキスト単位での部分適用が現実的である。中核ドメインのみイベントソーシングを採用し、周辺機能は従来型 CRUD で構築する構成が、費用対効果の面で有力な選択肢である。

イベントソーシングの本質は、技術的手法以上に「事実の記録を正とし、状態を派生情報と定義する」発想転換である。当該発想の理解が、適切な設計判断の前提条件である。
