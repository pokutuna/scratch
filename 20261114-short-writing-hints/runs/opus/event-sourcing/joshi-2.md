# イベントソーシング入門

## 1. イベントソーシングとは

通常のアプリケーションは、データベースに「現在の状態」だけを保存します。銀行口座なら残高の列を一つ持ち、入金や出金のたびにその値を書き換えます。この方式では、書き換える前の値は失われます。

イベントソーシングは、この発想を逆にします。状態そのものではなく、状態を変化させた出来事(イベント)を順に記録します。現在の状態は、それらのイベントを先頭から再生して導き出します。口座の例では、「口座を開設した」「1万円を入金した」「3千円を出金した」というイベントを追記していき、残高はイベントを畳み込んで7千円と計算します。

記録したイベントは、変更も削除もしません。誤りがあった場合も過去の記録は直さず、取り消しを表す新しいイベントを追加します。会計の帳簿で、誤記を消さずに反対仕訳で訂正するのと同じ考え方です。

## 2. 基本的な構成要素

イベントソーシングを採用したシステムは、おおむね次の要素で構成されます。

- **イベント**:過去に起きた事実を表す不変のデータです。「OrderPlaced」「ItemShipped」のように過去形で名付けるのが慣例です。
- **イベントストア**:イベントを追記専用で保存するストレージです。集約ごとにイベント列(ストリーム)を管理し、その順序を保証します。
- **集約(Aggregate)**:整合性を守る単位です。コマンドを受け取ると、ビジネスルールを検証したうえでイベントを発行します。
- **プロジェクション**:イベントを読み込み、参照用のデータ(リードモデル)を組み立てる処理です。

状態の復元は、次のような関数で表せます。

```typescript
type Event =
  | { type: "Deposited"; amount: number }
  | { type: "Withdrawn"; amount: number };

function apply(balance: number, e: Event): number {
  switch (e.type) {
    case "Deposited": return balance + e.amount;
    case "Withdrawn": return balance - e.amount;
  }
}

const balance = events.reduce(apply, 0);
```

コマンドは、「イベント列から現在の状態を復元し、ルールを検証し、新しいイベントを追記する」という流れで処理します。追記の際には、読み込んだ時点のバージョン番号を添えて楽観的排他制御を行うのが一般的です。別の処理が先に追記していればバージョンが一致しないため、書き込みは失敗します。

## 3. 得られる利点

最大の利点は、変更の履歴が完全に残ることです。いつ、何が、どの順で起きたのかを後から正確にたどれるので、監査や障害調査に強くなります。「なぜこの値になったのか」という問いにも、ログから推測することなく答えられます。

次に、過去の任意の時点の状態を再現できます。イベントを特定の時刻まで再生すれば、その時点の状態が得られます。これは不具合の再現や、過去データを用いた検証に役立ちます。

さらに、参照用のモデルを後から自由に追加できます。一次データであるイベントが残っているため、新しい集計や画面が必要になっても、プロジェクションを書いて全イベントを流し直せば済みます。現在の状態だけを保存する方式では、一度捨てた情報を後から取り戻せません。

加えて、イベントは他のシステムとの連携にも使えます。たとえば、注文確定のイベントを購読して在庫サービスや配送サービスを動かすといった、イベント駆動の設計と自然に組み合わせられます。

## 4. 注意すべき課題

こうした利点がある一方で、導入には相応の代償が伴います。

まず、読み取りが単純ではありません。イベント列をそのまま検索するのは非効率なので、多くの場合は CQRS(コマンドとクエリの責務分離)を採用し、書き込み側とは別にリードモデルを用意します。リードモデルは非同期に更新されることが多く、書き込んだ結果が直後の読み取りには反映されていない状態、つまり「結果整合性」を受け入れる必要があります。

次に、イベントのスキーマを変更しにくい点が挙げられます。過去のイベントは書き換えないため、フィールドを追加したり意味を変えたりするときは、古い形式も読めるようにしておかなければなりません。読み込み時に新しい形式へ変換するアップキャストや、イベント型のバージョン管理といった手法で対処します。

また、イベントが増えるほど、状態の復元に時間がかかります。この対策としては、ある時点の状態をスナップショットとして保存し、それ以降のイベントだけを再生する方法がよく使われます。

個人情報の扱いにも注意が要ります。イベントを削除しないという原則は、データの削除を求める法規制と衝突しかねません。個人情報をイベントとは別の場所に保存し、イベントには参照だけを持たせる方法があります。利用者ごとの鍵で暗号化しておき、削除を求められたら鍵を破棄する方法(クリプトシュレッディング)も知られています。

## 5. 導入を判断する観点

イベントソーシングは万能ではありません。単純な CRUD で足りるアプリケーションに適用しても、増える複雑さに見合う効果は得られません。

導入を検討する価値があるのは、たとえば次のような場合です。

- 金融、会計、物流など、変更の履歴そのものに業務上の価値がある
- 監査要件が厳しく、操作の経緯を説明する責任を負っている
- 同じデータから多様な参照モデルを作る必要がある
- 業務の流れが複雑で、ドメイン上の出来事を明示的に扱いたい

反対に、チームにイベント駆動設計の経験が乏しい場合や、結果整合性を許容できない要件が多い場合は、慎重に判断すべきです。システム全体ではなく、履歴が重要な一部の境界づけられたコンテキストに限って適用するのも現実的な選択肢です。

## 6. まとめ

イベントソーシングは、状態ではなく出来事を記録の中心に置く設計手法です。完全な履歴が残る、任意の時点を再現できる、参照モデルを柔軟に追加できるといった強みがあります。その一方で、結果整合性、スキーマの進化、データ削除への対応という課題も抱えています。両者を比較し、ドメインの性質に合う箇所で選択的に使うことが、導入を成功させる鍵となります。

**助詞・助動詞・接続詞で見直した主な点**

- **助詞**:「代償を伴う」のような誤った格助詞を「代償が伴う」に直しました。また、「の」が三つ以上続く箇所や、「は」と「が」が同じ文で競合する箇所を解消しました。
- **助動詞**:「〜することができる」を「〜できる」に縮め、文末を「です・ます」に統一しました。そのうえで、「〜します」「〜できます」「〜があります」と文末の形を散らし、単調さを避けました。
- **接続詞**:論点の並べ方を「まず/次に/さらに/加えて」「また」で整理しました。対比には「一方で」「反対に」を使い分け、逆接の「が」で文をつなぎ続けないよう、文を区切っています。
