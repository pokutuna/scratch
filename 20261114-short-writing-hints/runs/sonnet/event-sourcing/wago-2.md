# イベントソーシング入門

## 1. 概要

イベントソーシング(Event Sourcing)は、システムの状態を「現在値」ではなく「イベントの時系列」として永続化する設計パターンである。従来の CRUD 方式は UPDATE で既存レコードを上書きし、変更の履歴を喪失する。イベントソーシングは状態変化の事実を Append-only で記録し、現在状態は全イベントの再生(Replay)により導出する。

典型例は銀行口座である。「残高 7,000 円」という現在値のみを保存する設計では、入金と出金の経緯は不明である。「口座開設」「10,000 円入金」「3,000 円出金」という事実列を保存する設計では、任意時点の残高を正確に再現可能である。会計の元帳(Ledger)も同一の思想であり、訂正は消去ではなく修正仕訳の追加で実施する。

## 2. 基本概念

主要な用語は以下の通りである。

- **イベント**: 過去に発生した事実。過去形で命名する(例: `MoneyDeposited`)。不変(Immutable)であり、更新と削除は不可である。
- **コマンド**: 操作の意図の表明(例: `DepositMoney`)。検証により拒否が可能であり、イベントとは明確に区別する。
- **Aggregate**: 整合性の境界を形成するエンティティの集合。コマンドを受理し、検証後にイベントを生成する。
- **イベントストア**: イベントを保存する Append-only のデータストア。各ストリーム(通常は Aggregate 単位)で順序を保証する。
- **プロジェクション**: イベント列から生成する参照用モデル。Read Model とも称する。
- **スナップショット**: 特定時点の状態の複製。Replay のコスト削減を目的とする。

現在状態は、イベント列に対する fold 演算で導出する。

```typescript
type Event =
  | { type: "AccountOpened" }
  | { type: "MoneyDeposited"; amount: number }
  | { type: "MoneyWithdrawn"; amount: number };

function apply(balance: number, e: Event): number {
  switch (e.type) {
    case "AccountOpened":  return 0;
    case "MoneyDeposited": return balance + e.amount;
    case "MoneyWithdrawn": return balance - e.amount;
  }
}

const balance = events.reduce(apply, 0);
```

`apply` は純粋関数であり、副作用を保持しない。この性質により、Replay の結果は常に決定的である。

## 3. 処理フローと関連パターン

標準的なコマンド処理は、以下の手順で進行する。

1. コマンドを受信する。
2. 対象 Aggregate のイベント列をロードし、Replay で現在状態を復元する。スナップショットが存在する場合は、起点として使用する。
3. ビジネスルールを検証し、新規イベントを生成する。
4. イベントストアへ Append する。バージョン番号による楽観的並行制御(Optimistic Concurrency)で、競合を検出する。
5. 永続化の完了後、イベントを Subscriber へ配信し、プロジェクションを更新する。

関連パターンとして、**CQRS**(Command Query Responsibility Segregation)との併用が一般的である。更新系はイベントストア、参照系は用途別に最適化した Read Model が担当し、双方を独立に拡張可能である。

プロジェクションの更新は通常、非同期である。結果として、更新直後の参照に遅延が発生する。この性質を結果整合性(Eventual Consistency)と称する。イベントの永続化と配信の原子性を保証する手段として、Outbox パターンが有効である。

## 4. 利点と課題

### 利点

- **完全な監査証跡**: 全変更が事実として残存し、監査要件に直接対応する。
- **時間軸の分析**: 過去の任意時点の状態を再現可能であり、履歴分析や仮説検証が容易である。
- **障害の再現**: 本番のイベント列を開発環境で Replay し、不具合を再現できる。
- **Read Model の追加が容易**: 新規の参照要件は、既存イベントを再生して新規プロジェクションを構築するだけで対応可能である。
- **ドメインとの親和性**: イベントが業務の言語そのものであり、DDD(ドメイン駆動設計)と相性が良い。
- **追記処理の高速性**: Append-only は更新競合が少なく、高スループットを実現しやすい。

### 課題

- **学習コストと複雑性**: 概念が多く、チーム全体の習熟が必須である。
- **スキーマ進化**: イベントは不変であり、旧形式が永続的に残存する。Versioning と Upcasting(旧形式から新形式への変換)の戦略が必要である。
- **結果整合性への対応**: UI 設計と業務フローの両面で、遅延を許容する配慮が必要である。
- **削除要件との衝突**: GDPR の消去権と不変性は矛盾する。対策として Crypto Shredding(個人情報を暗号化し、鍵の破棄で無効化する手法)が存在する。
- **クエリの制約**: イベントストア単体では集計や検索が不得手であり、プロジェクションが実質的に必須である。
- **Replay の長大化**: ストリームの肥大に対し、スナップショットの運用が必要である。

## 5. 導入判断と設計指針

### 適合領域と不適合領域

適合するのは、金融、決済、在庫管理、受注管理など、監査要件が厳格で業務ルールが複雑なドメインである。履歴の価値が高く、状態遷移そのものが業務の中核である場合に、効果が最大化する。

不適合なのは、単純な CRUD 中心の管理画面、履歴が不要なシステム、小規模かつ短期のプロジェクトである。採用の判断は、「履歴の価値」と「運用の複雑性」の比較で実施する。

### 設計指針

1. **限定採用**: システム全体ではなく、必要な Bounded Context のみに適用する。
2. **業務的な命名**: イベント名は業務上の意味を反映する(例: `OrderPlaced`)。`OrderUpdated` のような汎用名は禁止とする。
3. **自己完結したイベント**: 処理に必要な情報を、イベント自体に内包する。外部参照への依存は、Replay の再現性を破壊する。
4. **Versioning の事前策定**: 初期段階でスキーマ進化の方針を決定する。
5. **冪等なプロジェクション**: 再配信を想定し、同一イベントの重複処理で結果が変化しない実装とする。
6. **既存基盤の活用**: EventStoreDB、Axon Framework、Marten などの専用製品、または PostgreSQL 上の独自実装から選択する。独自実装は、順序保証と並行制御の検証コストに注意が必要である。

イベントソーシングは万能の解法ではなく、トレードオフの明確なパターンである。要件と運用体制を精査した上で、局所的に導入する方針を推奨する。
