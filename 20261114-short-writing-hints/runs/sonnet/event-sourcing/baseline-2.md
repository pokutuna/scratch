# イベントソーシング入門

## 1. イベントソーシングとは

イベントソーシング(Event Sourcing)は、アプリケーションの状態を「現在の値」として保存するのではなく、**状態を変化させた出来事(イベント)の列**として保存する設計パターンです。現在の状態は、保存されたイベントを先頭から順に適用(リプレイ)することで導出します。

従来の CRUD では、たとえば口座残高を `balance = 7000` というカラムで持ち、入出金のたびに `UPDATE` で上書きします。この方式では「なぜ 7000 になったのか」という履歴は失われます。イベントソーシングでは次のように記録します。

```
AccountOpened   { accountId: "A1", initial: 0 }
MoneyDeposited  { accountId: "A1", amount: 10000 }
MoneyWithdrawn  { accountId: "A1", amount: 3000 }
```

残高 7000 はこの 3 件を畳み込んだ結果にすぎません。イベントは **追記のみ(append-only)** で、更新も削除もしません。これが最も重要な性質です。

イベントは「過去に起きた事実」なので、名前は過去形で付けます(`OrderPlaced`、`EmailChanged` など)。「〜しろ」という意図を表すコマンド(`PlaceOrder`)とは明確に区別します。コマンドは拒否され得ますが、イベントは既に起きた事実として受け入れるしかありません。

## 2. 基本的な仕組み

### イベントストア

イベントを保存するデータストアをイベントストアと呼びます。多くの場合、集約(Aggregate)ごとのストリームとして管理され、次のような情報を持ちます。

- ストリーム ID(集約の ID)
- バージョン(ストリーム内での連番)
- イベント種別とペイロード
- メタデータ(発生時刻、因果関係 ID、実行ユーザーなど)

RDB でも実装でき、専用製品(EventStoreDB など)やメッセージ基盤を使う選択肢もあります。

### 状態の復元

集約をロードするときは、該当ストリームのイベントを読み出し、状態に畳み込みます。

```typescript
type Event =
  | { type: "Deposited"; amount: number }
  | { type: "Withdrawn"; amount: number };

type State = { balance: number };

const apply = (state: State, event: Event): State => {
  switch (event.type) {
    case "Deposited": return { balance: state.balance + event.amount };
    case "Withdrawn": return { balance: state.balance - event.amount };
  }
};

const load = (events: Event[]): State =>
  events.reduce(apply, { balance: 0 });
```

### コマンドの処理

書き込みは「ロード → 判断 → イベント追記」の流れです。出金コマンドなら、現在の状態から残高が足りるか検証し、問題なければ `Withdrawn` イベントを追加します。

同時更新の衝突は、**楽観的ロック**で防ぎます。ロード時のバージョンを覚えておき、追記時に「ストリームの最新バージョンが期待値と一致する場合のみ成功」とします。

### スナップショット

イベントが数千、数万件に増えるとリプレイが遅くなります。そこで、一定件数ごとに状態のスナップショットを保存し、「スナップショット + それ以降のイベント」で復元する最適化を行います。スナップショットはあくまで派生データであり、真実の源(source of truth)はイベント列です。

## 3. CQRS との関係と読み取りモデル

イベントソーシングでは、イベント列から任意の条件で検索・集計するのが難しくなります。たとえば「残高が 1 万円以上の口座一覧」をその都度全ストリームのリプレイで求めるのは現実的ではありません。

そこで、**CQRS(Command Query Responsibility Segregation)** と組み合わせるのが一般的です。書き込み側はイベントストアに追記し、読み取り側はイベントを購読して、クエリに最適化した **プロジェクション(読み取りモデル)** を構築します。

```
Command → Aggregate → Event Store → (購読) → Projection → Query
```

プロジェクションは RDB のテーブル、検索エンジン、キャッシュなど何でもかまいません。用途ごとに複数作れますし、壊れても破棄してイベントを最初から流し直せば再構築できます。これは大きな利点です。

一方、プロジェクションの更新は非同期になることが多く、**結果整合性**を受け入れる必要があります。書き込み直後に読み取っても反映されていない可能性があるため、UI の設計や API の返し方で配慮が要ります。

なお、イベントソーシングと CQRS は別の概念です。CQRS 単体でも使えますが、イベントソーシングを採用すると読み取りモデルの分離がほぼ必須になるため、セットで語られることが多いのです。

## 4. メリット

- **完全な監査証跡**:すべての変更が履歴として残るため、金融や医療など追跡性が求められる領域に向いています。
- **時間遡行とデバッグ**:任意の時点の状態を再現できます。本番で起きた不具合を、同じイベント列で再現することも可能です。
- **後からの分析・機能追加**:当時は想定していなかった集計や新しい読み取りモデルを、過去のイベントから遡って作れます。CRUD では捨てられていた情報が資産になります。
- **イベント駆動との親和性**:イベントが自然に他サービスへの連携の起点になります。
- **書き込み性能**:追記のみなので、書き込みの競合や更新コストを抑えやすい特性があります。

## 5. デメリットと注意点

イベントソーシングは強力ですが、導入コストは小さくありません。

### イベントスキーマの進化

イベントは不変で永続するため、後からスキーマを変えるのが難題です。対策としては次のようなものがあります。

- 新しいフィールドは任意項目として追加する(後方互換を保つ)
- 読み込み時にイベントを新バージョンへ変換する **アップキャスト** を用意する
- イベントにバージョン番号を持たせる

イベントの設計は最初が肝心で、単なる「テーブルの変更差分」ではなく、**ビジネス上意味のある出来事** として粒度と名前を決めるべきです。

### 結果整合性と複雑さ

読み取りモデルの遅延、イベントの重複配信(冪等なハンドラが必要)、順序保証など、考えることが増えます。チームに分散システムの知識が求められます。

### 削除とプライバシー

追記のみという性質は、GDPR などの「忘れられる権利」と衝突します。個人情報を直接イベントに入れず、暗号化して鍵を別管理し、削除時は鍵を破棄する **crypto-shredding** がよく使われます。

### 向かないケース

単純な CRUD で十分なシステム、履歴に価値がない領域、チームが不慣れな状況では、導入の費用対効果が合いません。システム全体に適用せず、**履歴が価値を持つ境界づけられたコンテキストだけ** に使うのが現実的です。

## 6. 導入のヒント

1. **小さく始める**:まず 1 つの集約、1 つのコンテキストで試し、運用の感覚をつかみます。
2. **イベントはドメイン言語で命名する**:`StatusUpdated` のような曖昧な名前ではなく、`OrderShipped` のように意図が伝わる名前にします。ドメイン駆動設計やイベントストーミングと相性が良いです。
3. **プロジェクションは再構築可能に保つ**:リプレイで作り直せる前提で設計し、その手順も運用に組み込みます。
4. **ハンドラは冪等にする**:少なくとも 1 回(at-least-once)の配信を前提に、重複しても結果が変わらないようにします。
5. **スナップショットは後回しにする**:計測して必要になってから導入します。早すぎる最適化は避けましょう。

イベントソーシングは「状態ではなく変化を記録する」という発想の転換です。履歴そのものが価値になる領域では強力な武器になりますが、複雑さも伴います。自分たちの課題に本当に必要かを見極めたうえで、適用範囲を絞って採用することが成功の鍵です。
