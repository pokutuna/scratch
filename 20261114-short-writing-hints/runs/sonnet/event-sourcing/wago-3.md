# イベントソーシング解説

## 1. 概要と基本概念

イベントソーシング（Event Sourcing、以下 ES）は、システムの状態を「現在値」ではなく「イベントの時系列」として永続化する設計パターンである。

従来の CRUD 型システムは、UPDATE 文で最新状態を上書きするため、過去の経緯が消失する。ES では、状態変更の事実を **Immutable** なイベントとして **Append-only** で記録する。現在の状態は、保存済みイベント列を先頭から **Replay** して導出する。

銀行口座で例示する。「残高 1,000 円」という結果を保存する代わりに、以下の事実を順番に記録する。

1. 口座開設
2. 1,500 円入金
3. 500 円出金

この 3 件を順次適用すると、残高 1,000 円が復元される。結果ではなく原因を保存する点が、ES の本質である。

イベントは「発生済みの事実」であり、変更も削除も禁止である。命名は過去形（`OrderPlaced`、`Deposited` など）を採用し、ドメイン専門家が使用するユビキタス言語と一致させる。

## 2. 基本アーキテクチャ

ES の構成要素は、主に以下の 4 点である。

**イベントストア（Event Store）**
イベントを永続化する専用のストレージである。ストリーム（通常は Aggregate 単位）ごとにイベントを管理し、追記のみを許可する。同時更新の衝突は、**Optimistic Concurrency Control** で制御する。書込時に「期待バージョン」を指定し、実際のバージョンと相違する場合は拒否する。

**アグリゲート（Aggregate）**
整合性の境界を定義するドメインオブジェクトである。処理の流れは次の通り。

1. コマンドを受信する
2. 過去のイベントを Replay して現在状態を構築する
3. ビジネスルールを検証する
4. 新規イベントを生成してストアへ追加する

**プロジェクション（Projection）**
イベント列を購読し、参照用の **Read Model** を構築する機構である。RDB のテーブル、Elasticsearch の索引、Redis のキャッシュなど、用途別に最適な形式を選択できる。

**コマンドとイベントの区別**
コマンドは「意図」（`Withdraw`）であり、拒否される可能性がある。イベントは「結果」（`Withdrawn`）であり、拒否は不可能である。この区別が設計の基本となる。

状態復元のコードを TypeScript で例示する。

```typescript
type AccountEvent =
  | { type: "AccountOpened"; accountId: string }
  | { type: "Deposited"; amount: number }
  | { type: "Withdrawn"; amount: number };

// イベントを 1 件適用して次の状態を返却する純粋関数
const apply = (balance: number, e: AccountEvent): number => {
  switch (e.type) {
    case "Deposited": return balance + e.amount;
    case "Withdrawn": return balance - e.amount;
    default: return balance;
  }
};

// Replay による現在状態の復元
const current = events.reduce(apply, 0);
```

## 3. 代表的な実装パターン

**CQRS との併用**
ES は **CQRS**（Command Query Responsibility Segregation）と併用する構成が一般的である。更新系（イベントストア）と参照系（Read Model）を分離し、独立にスケール可能とする。ES 単体でも成立するが、イベント列への直接クエリは非効率であるため、実運用ではほぼ必須の組合せとなる。

**スナップショット（Snapshot）**
イベント数が増大すると、Replay のコストが上昇する。対策として、一定間隔（例：100 イベントごと）で状態のスナップショットを保存する。復元時は、最新スナップショットとそれ以降の差分イベントのみを適用する。スナップショットは性能最適化の手段であり、正本はあくまでイベント列である。

**スキーマ進化（Event Versioning）**
イベントは永続的に保存されるため、仕様変更への対応が重要となる。代表的な手法は **Upcasting** である。旧バージョンのイベントを読込時に最新形式へ変換する。保存済みデータの書換は行わない。

**Outbox パターン**
イベント保存と外部システムへの通知を、整合的に実行する手法である。イベントと同一トランザクションで Outbox テーブルへ記録し、別プロセスがメッセージブローカー（Kafka など）へ転送する。二重書込による不整合を回避できる。

**冪等性（Idempotency）**
配信は At-least-once が基本であり、重複受信が発生する。プロジェクションとコンシューマは、イベント ID やシーケンス番号による重複排除を実装する必要がある。

## 4. メリット

**完全な監査証跡（Audit Trail）**
全変更が時系列で保存されるため、「誰が、いつ、何を実行したか」を完全に追跡できる。金融、医療、法務など、厳格な監査要件を持つ領域で大きな価値を発揮する。

**時間遡及（Temporal Query）**
任意時点の状態を再構築できる。障害の原因調査では、過去の状態を再現してデバッグできる。「3 か月前の時点では在庫が何個だったか」という分析も可能である。

**Read Model の柔軟性**
新規要件で別形式のデータが必要になっても、過去のイベントを再投影すれば構築できる。事前の履歴保存が不要であり、将来の分析需要にも対応可能である。

**イベント駆動統合との親和性**
イベントは、そのままドメインイベントとして他のサービスへ配信できる。マイクロサービス間の疎結合な連携を実現しやすい。

**ビジネス分析の価値**
状態の「結果」だけでなく「過程」が蓄積される。例えば EC サイトでは、カートへの追加後に削除した商品といった行動データも保存され、マーケティング分析に活用できる。

## 5. デメリットと課題

**学習コストと設計難度**
CRUD とは思考モデルが大きく相違する。イベントの粒度設計、Aggregate の境界設定、命名規則など、ドメイン駆動設計（DDD）の知見が必要となる。チーム全体の習熟に時間を要する。

**結果整合性（Eventual Consistency）**
Read Model の更新は非同期であり、書込直後の参照で古いデータを取得する可能性がある。UI 設計では、楽観的更新や遅延表示への配慮が必要である。

**イベントスキーマの変更**
不変であるイベントは、設計ミスの修正が困難である。誤ったイベントを削除せず、補正イベント（Compensating Event）を追加して対応する。長期運用では、Upcaster の管理負担も増加する。

**個人情報の削除要求**
GDPR などの「忘れられる権利」と、不変性の原則は衝突する。対策として、個人情報のみを暗号化して保存し、削除要求時に鍵を破棄する **Crypto-shredding** が採用される。

**運用の複雑性**
プロジェクションの再構築、ストレージの肥大化、監視対象の増加など、運用負荷は上昇する。Replay に数時間を要する規模では、無停止での再構築戦略も必要となる。

## 6. 採用判断のガイドライン

**適合しやすい領域**
- 金融、決済、会計など、監査要件が厳格なシステム
- 注文、在庫、物流など、状態遷移が重要なドメイン
- 履歴分析や時間遡及が価値を持つ業務
- イベント駆動アーキテクチャを前提とした基盤

**適合しにくい領域**
- 単純な CRUD で十分な管理画面
- 履歴が不要で、即時の強整合性が必須のシステム
- DDD に習熟した人員が不足しているチーム

**段階的な導入**
システム全体に ES を適用する必要はない。まず、価値が高い Bounded Context に限定して導入し、他の領域は従来の RDB で運用する構成が現実的である。

**代表的なツール**
- **EventStoreDB**（現 KurrentDB）: ES 専用のデータベース
- **Axon Framework**: JVM 系の ES/CQRS フレームワーク
- **PostgreSQL**: イベントテーブルによる自前実装
- **Apache Kafka**: ストリーム基盤、ただし長期保存の正本としては設計判断が必要

ES は強力なパターンであるが、万能ではない。「履歴が資産となるドメインか」を最初に確認し、複雑性と便益のバランスを評価した上で採用を判断すべきである。
