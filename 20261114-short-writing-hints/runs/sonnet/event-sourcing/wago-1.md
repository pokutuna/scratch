# イベントソーシング解説

## 1. 概要

イベントソーシング(Event Sourcing、以下 ES)は、システムの状態を「現在値」ではなく「イベントの時系列」として永続化する設計パターンである。

従来の CRUD モデルは UPDATE や DELETE で状態を上書きするので、変更の履歴は原則として消失する。ES は逆に、発生した事実をイベントとして Append-only で保存する。現在の状態は、保存済みイベントの集約によって導出する。

銀行口座を具体例とする。CRUD は「残高 = 8,000 円」という最終結果のみを保持する。ES は「口座開設」「10,000 円入金」「2,000 円出金」という事実の系列を保持し、残高はその総和として計算する。会計の台帳と同一の思想であり、訂正は消去ではなく、逆方向の仕訳(補償イベント)の追加で実施する。

## 2. 基本概念

ES を理解する際の主要な構成要素を整理する。

- **イベント(Event)**: 過去に発生した事実。Immutable であり、変更や削除は禁止する。命名は過去分詞形(`OrderPlaced`、`PaymentCompleted`)が慣例である。
- **コマンド(Command)**: 状態変更の要求。拒否が可能であり、イベントとは区別する。命令形で命名する(`PlaceOrder`)。
- **アグリゲート(Aggregate)**: 整合性の境界。コマンドを受信し、現在状態に対して検証を実行して、新規イベントを生成する。
- **イベントストア(Event Store)**: イベントの永続層。Aggregate ID 単位の「ストリーム」を管理し、バージョン番号による楽観的排他制御(Optimistic Concurrency)を提供する。
- **リプレイ(Replay)**: 初期状態に全イベントを順次適用して、現在状態を復元する処理。
- **スナップショット(Snapshot)**: 特定バージョンの状態を保存する最適化手法。リプレイの対象を差分のみに限定する。

## 3. 実装の骨格

状態遷移を「純粋関数」として定義するのが基本である。TypeScript による最小構成を示す。

```typescript
type Event =
  | { type: "AccountOpened" }
  | { type: "MoneyDeposited"; amount: number }
  | { type: "MoneyWithdrawn"; amount: number };

type State = { balance: number };

// イベント適用: 副作用なし、検証なし
function apply(state: State, event: Event): State {
  switch (event.type) {
    case "AccountOpened":  return { balance: 0 };
    case "MoneyDeposited": return { balance: state.balance + event.amount };
    case "MoneyWithdrawn": return { balance: state.balance - event.amount };
  }
}

// コマンド処理: 検証を実施し、イベントを返却
function withdraw(state: State, amount: number): Event[] {
  if (state.balance < amount) throw new Error("InsufficientBalance");
  return [{ type: "MoneyWithdrawn", amount }];
}

// リプレイ
const state = storedEvents.reduce(apply, { balance: 0 });
```

重要な原則は 2 点である。

1. `apply` には検証ロジックを配置しない。イベントは既に確定した事実であり、リプレイ時に拒否は不可能である。
2. 検証とビジネスルールはコマンド処理に集約する。

保存時は「期待バージョン」を指定して Append する。同一ストリームへの並行更新が発生した場合、後続のトランザクションはバージョン競合で失敗し、リトライまたはエラー応答となる。

## 4. CQRS とプロジェクション

ES は CQRS(Command Query Responsibility Segregation)と併用する構成が多い。イベント列は更新側の記録としては優秀だが、「ユーザー一覧を条件検索」といった参照用途には不向きだからである。

そこでイベントを購読し、参照専用のデータ構造へ変換する **プロジェクション(Projection)** を配置する。出力先は RDB、Elasticsearch、Redis など任意であり、用途ごとに複数の **リードモデル(Read Model)** を独立して構築できる。

この構成では **結果整合性(Eventual Consistency)** が前提となる。イベント保存からプロジェクション反映までに遅延が発生するので、UI 設計やAPI 契約でその事実を考慮する必要がある。具体策として、更新直後はコマンド応答のデータを表示する、バージョン番号で反映を確認する、などの手法が存在する。

プロジェクションは破棄と再構築が可能である。バグ修正や新規要件の追加時は、全イベントを先頭から再処理して新規リードモデルを生成すればよい。この性質が ES の最大級の利点である。

## 5. 利点と課題

### 利点

- **完全な監査証跡**: 全変更の履歴が自動的に保存される。金融や医療など、規制要件の厳格な領域で有効である。
- **時間軸の遡行**: 任意時点の状態を再現可能であり、障害の原因調査やバグの再現に有用である。
- **分析と拡張の柔軟性**: 過去データを新規の観点で再解釈できる。「後日必要になった集計」にも遡及対応が可能である。
- **イベント駆動連携**: イベントを他サービスへ配信すれば、疎結合な統合を実現できる。

### 課題

- **スキーマ進化**: イベントは不変なので、定義変更には Upcasting(旧版イベントの変換)や版管理が必要である。設計初期のイベント粒度が重要となる。
- **結果整合性の複雑性**: 開発者と利用者の双方に、認識の転換を要求する。
- **データ削除要求**: GDPR などの「削除権」と Immutable の原則が衝突する。個人情報を暗号化し、鍵の破棄で無効化する Crypto Shredding が代表的な対策である。
- **運用負荷**: ストリーム肥大化への対処(スナップショット、アーカイブ)、プロジェクションの監視、再構築の手順整備が必要である。
- **学習コスト**: チーム全体の理解が不足していると、設計の破綻を招きやすい。

## 6. 採用判断の指針

ES は強力だが、万能の解決策ではない。導入の可否は以下の観点で判断する。

**適合するドメイン**

- 監査と履歴が要件であるシステム(決済、会計、在庫、契約管理)
- 状態遷移そのものがビジネスの価値を持つ領域(注文、ワークフロー)
- 分析用途で過去データの再解釈が頻発する領域

**不適合なドメイン**

- 単純な CRUD で十分な管理画面系システム
- 履歴が不要で、更新頻度の高いキャッシュ的データ
- ES の経験がないチームによる、短期納期のプロジェクト

実務上の推奨は **段階的導入** である。システム全体に適用せず、価値の大きい境界づけられたコンテキスト(Bounded Context)に限定して採用する。実装は専用製品(EventStoreDB、Axon など)か、既存 RDB 上の自前実装から選択する。小規模な検証では、PostgreSQL に `(stream_id, version, type, payload)` を持つテーブルを配置する構成でも、基本機能は十分に実現可能である。

最後に、ES は技術選定である以前に、ドメインモデリングの手法である。イベントの粒度と命名にビジネスの知識を反映させる作業、すなわちイベントストーミング(Event Storming)などによるドメインエキスパートとの協調が、成否を左右する。
