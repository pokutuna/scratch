# イベントソーシング入門

## 1. イベントソーシングとは

イベントソーシング(Event Sourcing)は、アプリケーションの状態を「現在の値」ではなく「状態を変化させた出来事(イベント)の列」として保存するアーキテクチャパターンです。現在の状態は、保存されたイベントを先頭から順に適用(リプレイ)することで導出します。

一般的な CRUD では、たとえば口座残高を `balance = 7000` というカラムで保持し、入出金のたびに UPDATE で上書きします。この方式では「なぜ 7000 になったのか」という経緯は失われます。イベントソーシングでは次のように事実を追記していきます。

```
AccountOpened   { accountId: "A1", owner: "taro" }
MoneyDeposited  { accountId: "A1", amount: 10000 }
MoneyWithdrawn  { accountId: "A1", amount: 3000 }
```

現在の残高は 0 + 10000 − 3000 = 7000 と計算できます。身近な例では、Git のコミット履歴や会計の仕訳帳、データベースの WAL(Write-Ahead Log)が同じ発想に基づいています。

### 基本原則

- **イベントは不変(immutable)**:一度保存したイベントは書き換えず、削除もしません。
- **追記のみ(append-only)**:誤りがあれば、それを打ち消す補正イベントを新たに追加します。
- **イベントは過去形で命名する**:`OrderPlaced`、`AddressChanged` のように、すでに起きた事実として表現します。

## 2. 基本的な構成要素

### イベントストア

イベントを永続化するデータストアです。最低限、次の操作を提供します。

- ストリーム(通常は集約ごと)の末尾へのイベント追記
- ストリーム単位でのイベント読み出し

RDB でも実装でき、専用製品(EventStoreDB など)や、Kafka のようなログ基盤を使う選択肢もあります。単純なテーブル設計の例を示します。

```sql
CREATE TABLE events (
  stream_id   VARCHAR(64) NOT NULL,
  version     INT         NOT NULL,
  event_type  VARCHAR(128) NOT NULL,
  payload     JSON        NOT NULL,
  occurred_at TIMESTAMP   NOT NULL,
  PRIMARY KEY (stream_id, version)
);
```

`(stream_id, version)` を主キーにすることで、後述する楽観的排他制御を自然に実現できます。

### 集約(Aggregate)

DDD の集約と相性がよく、ひとつの整合性境界がひとつのイベントストリームに対応します。集約はコマンドを受け取り、ビジネスルールを検証したうえで、新しいイベントを生成します。状態の更新は「イベントの適用」関数に集約します。

```typescript
class Account {
  balance = 0;
  version = 0;

  apply(event: AccountEvent) {
    switch (event.type) {
      case "MoneyDeposited": this.balance += event.amount; break;
      case "MoneyWithdrawn": this.balance -= event.amount; break;
    }
    this.version++;
  }

  withdraw(amount: number): AccountEvent[] {
    if (this.balance < amount) throw new Error("残高不足");
    return [{ type: "MoneyWithdrawn", amount }];
  }
}
```

重要なのは、**検証はコマンド処理時に行い、`apply` は検証せず状態を変えるだけにする**点です。過去のイベントは常に正しい事実なので、リプレイ時に拒否してはいけません。

## 3. CQRS との組み合わせ

イベントソーシングは CQRS(Command Query Responsibility Segregation)と組み合わせて使われることが多いパターンです。イベント列は書き込みには適していますが、「残高が 5000 円以上の口座一覧」のような検索には向きません。そこで読み取り側を分離します。

1. コマンドが集約に届き、イベントが生成されてイベントストアに追記される
2. 追記されたイベントを **プロジェクション(Projection)** が購読する
3. プロジェクションがイベントを元に、検索に最適化された **リードモデル** を更新する

リードモデルは RDB、全文検索エンジン、キャッシュなど用途ごとに自由に選べます。しかもイベントさえ残っていれば、リードモデルはいつでも破棄して作り直せます。新しい画面や集計要件が生じても、過去のイベントから新しいリードモデルを構築できる点は大きな利点です。

一方で、リードモデルの更新は非同期になることが多く、**結果整合性(eventual consistency)** を受け入れる必要があります。書き込み直後の画面で古いデータが表示されうるため、UI での扱い(楽観的な表示、処理中の明示など)を設計段階で考えておきます。

## 4. メリット

- **完全な監査証跡**:誰が・いつ・何をしたかが自然に記録されます。金融、医療、法務など監査要件の厳しい領域で有効です。
- **時間旅行とデバッグ**:任意の時点までイベントを適用すれば、その時点の状態を再現できます。本番の不具合も、イベント列を手元で再生して調査できます。
- **後からの分析・再構築**:当初は想定しなかった集計や、新しいリードモデルを過去分まで遡って作れます。
- **ドメインの表現力**:`AddressChanged` と `AddressCorrected` のように、単なる値の更新では区別できない業務上の意図を残せます。
- **イベント駆動との親和性**:イベントが一次情報なので、他システムへの連携やサーガによる長いプロセスの調整にそのまま使えます。

## 5. 課題と設計上の注意点

### スキーマ進化

イベントは不変なので、過去のイベントの形式が残り続けます。フィールドを追加・変更したくなったときの対策として、次のような手段があります。

- 読み出し時に旧バージョンを新バージョンへ変換する **アップキャスト**
- イベントにスキーマバージョンを持たせる
- 後方互換な変更(任意フィールドの追加)を基本にする

### リプレイ性能とスナップショット

イベントが数万件に達する集約では、毎回の全件リプレイは遅くなります。一定件数ごとに状態を保存する **スナップショット** で、「最新スナップショット+それ以降のイベント」だけを適用して高速化します。ただし、まず集約のライフサイクルを短くする(ストリームを適切に分割する)ことを検討してください。多くの場合、集約が肥大化していること自体が設計上の兆候です。

### 同時更新の制御

同じ集約への同時書き込みは、期待バージョンを指定した追記で防ぎます。`(stream_id, version)` の主キー違反が起きたら競合とみなし、最新状態を読み直してコマンドを再試行します。

### 削除とプライバシー

「イベントは削除しない」という原則は、GDPR などの忘れられる権利と衝突します。対策としては、個人情報をイベント本体ではなく別ストアに置いて参照だけ持つ方法や、個人ごとの暗号鍵でペイロードを暗号化し、鍵を破棄して実質的に読めなくする **crypto-shredding** があります。

### 学習コストと運用の複雑さ

結果整合性、プロジェクションの再構築、イベント設計など、考えるべきことが CRUD より増えます。チームの習熟度も重要な要素です。

## 6. 導入の判断基準

イベントソーシングは万能ではなく、**システム全体ではなく、必要な境界づけられたコンテキストに限定して適用する**のが現実的です。

**向いているケース**
- 変更履歴そのものがビジネス価値、または法的要件である
- 複雑なドメインで、状態遷移の経緯が重要
- 過去データに基づく分析や再計算を頻繁に行う

**向いていないケース**
- 単純なマスタ管理や設定情報など、CRUD で十分なもの
- 履歴が不要で、強い即時整合性が求められる画面中心の機能
- チームにイベント駆動の経験がなく、学習余裕もない

まずは小さな領域で試し、イベントの粒度やスキーマ進化の運用を学んでから適用範囲を広げることをおすすめします。履歴だけが目的であれば、監査ログテーブルやテンポラルテーブルのような軽量な代替手段も検討に値します。

### まとめ

イベントソーシングは「状態ではなく変化を記録する」ことで、監査性・再現性・拡張性を得る手法です。その代償として、設計と運用の複雑さを引き受けることになります。得られる価値が複雑さに見合う領域を見極めて採用することが、成功の鍵です。
