# イベントソーシング入門

## 1. イベントソーシングとは

イベントソーシング(Event Sourcing)は、アプリケーションの状態を「現在の値」ではなく「状態を変化させた出来事(イベント)の列」として保存する設計パターンです。現在の状態は、保存されたイベントを先頭から順に適用(リプレイ)することで再構築します。

一般的な CRUD アプリケーションでは、たとえば注文テーブルの `status` カラムを `PAID` から `SHIPPED` へ UPDATE します。この方式では更新後に過去の値が失われ、「いつ、誰が、なぜ変更したか」は別途ログを用意しない限り追えません。

イベントソーシングでは、次のようなイベントを追記(append)していきます。

```json
{ "type": "OrderPlaced",  "orderId": "o-1", "at": "2026-11-01T10:00:00Z" }
{ "type": "OrderPaid",    "orderId": "o-1", "at": "2026-11-01T10:05:00Z" }
{ "type": "OrderShipped", "orderId": "o-1", "at": "2026-11-02T09:00:00Z" }
```

この列を畳み込めば「o-1 は発送済み」という現在の状態が得られます。イベントは「起きた事実」なので、原則として更新も削除もしません。銀行の通帳や会計の仕訳帳が、残高だけでなく取引の履歴を記録するのと同じ発想です。

## 2. 基本的な構成要素

### イベント

過去に起きた事実を表すメッセージです。`OrderPaid` のように過去形で命名するのが慣例で、ドメインの言葉で意味が分かる粒度にします。`OrderUpdated` のような曖昧な名前は、何が起きたかを失わせるため避けます。

### イベントストア

イベントを追記専用で保存するデータストアです。最低限、次の機能が必要になります。

- 集約(aggregate)単位のストリームへの追記
- ストリームの先頭からの順次読み出し
- 楽観的排他制御のためのバージョン管理

専用製品(EventStoreDB など)のほか、RDB に `(stream_id, version, type, payload)` を持つテーブルを作り、`(stream_id, version)` に一意制約を張って実装することもよくあります。

### 集約とコマンド

コマンド(「支払う」「発送する」といった意図)を受け取った集約は、現在の状態を元に検証を行い、問題なければイベントを発行します。処理の流れは次のとおりです。

1. ストリームからイベントを読み出し、集約の状態を復元する
2. コマンドを検証する(例:未払いの注文は発送できない)
3. 新しいイベントを、読み込んだバージョンを期待値として追記する
4. 他のユーザーが先に追記していた場合は、バージョン衝突として失敗させ、再試行する

状態の復元は、概念的には次のような純粋関数の畳み込みです。

```typescript
const state = events.reduce(apply, initialState);
```

`apply` は副作用を持たず、イベントを状態に反映するだけに保つと、テストや再現が容易になります。

## 3. CQRS と射影(プロジェクション)

イベントの列は書き込みには適していますが、「ユーザー別の注文一覧」のような検索では毎回リプレイするのは非効率です。そこで多くの場合、CQRS(Command Query Responsibility Segregation)と組み合わせ、書き込みモデルと読み取りモデルを分離します。

読み取りモデルは、イベントを購読して更新される射影(プロジェクション)として作ります。

- イベントストアに追記されたイベントを購読する
- イベントごとに、読み取り用のテーブルやインデックス(RDB、検索エンジン、キャッシュなど)を更新する
- 用途ごとに複数の射影を持てる

射影はイベントから再生成できる「派生データ」です。そのため、画面の要件が変わったら新しい射影を作ってイベントを最初から流し直せます。スキーマ変更や新機能追加に強いのは大きな利点です。

一方で、書き込みから射影への反映は通常非同期のため、**結果整合性**を受け入れる必要があります。書き込み直後に読み取っても古い情報が返る可能性があり、UI での扱い(楽観的更新や処理中表示など)を設計段階で考えておきます。

## 4. 利点と注意すべき課題

### 利点

- **完全な監査ログ**:履歴が設計の中心にあり、事後に追加した記録ではないため、抜け漏れが起きにくい
- **時間を遡った分析**:過去の任意時点の状態を再現でき、不具合の調査や「もし別のロジックだったら」の検証ができる
- **柔軟な読み取りモデル**:後から新しい観点の集計を、過去分も含めて作れる
- **イベント駆動との相性**:他システムへの通知や連携のソースとして、そのままイベントを利用できる

### 課題

- **スキーマの進化**:イベントは不変で長期間残るため、型の変更に対応が必要。バージョン付き型、アップキャスト(旧イベントを読み込み時に新形式へ変換)などの戦略が要る
- **リプレイ性能**:ストリームが長くなると復元が遅くなる。一定件数ごとにスナップショットを保存して緩和する
- **結果整合性**:前節のとおり、読み取りの遅延を前提にした設計が必要
- **個人情報と削除**:不変の履歴は GDPR などの削除要求と衝突する。個人情報を暗号化し、鍵を破棄することで読めなくする「クリプトシュレッディング」などが使われる
- **学習・運用コスト**:チームに新しい考え方が求められ、デバッグや運用ツールも整える必要がある

## 5. 導入の判断基準と実践のヒント

イベントソーシングは万能ではなく、単純な CRUD で足りる領域に持ち込むと複雑さだけが増えます。次のような条件に当てはまる領域で検討する価値があります。

**向いているケース**

- 金融、在庫、予約、会計など、履歴や監査が業務上の要件になっている
- 状態遷移が複雑で、「なぜその状態になったか」が重要
- 同じ事実から複数の見え方(集計・分析)を作りたい

**向いていないケース**

- 設定やマスタデータなど、単純な登録・更新が中心
- 履歴に価値がなく、強い即時整合性が常に必要
- チームの経験が乏しく、学習コストを負担できない

導入するときは、次の点を意識すると失敗しにくくなります。

1. **システム全体に適用しない**:履歴が重要な境界づけられたコンテキストだけに使い、他は通常の方式にする
2. **イベント設計に時間をかける**:ドメインエキスパートと対話し、業務上の意味を持つ名前と粒度にする。イベントストーミングは有効な手法
3. **べき等性を確保する**:射影の更新やイベントの再配信は重複しうるため、同じイベントを二度処理しても結果が変わらないようにする
4. **射影の再構築手順を用意する**:リプレイして作り直す運用を、最初からテスト・自動化しておく
5. **スキーマ進化の方針を先に決める**:バージョニングとアップキャストの規約を、最初のイベントを保存する前に決める

## 6. まとめ

イベントソーシングは、状態そのものではなく「状態を変えた事実」を一次データとして保存する設計です。履歴の完全性、過去の再現、柔軟な読み取りモデルといった強力な利点がある一方、スキーマ進化、結果整合性、運用の複雑さといったコストを伴います。

大切なのは、技術的な流行としてではなく、履歴そのものに業務価値があるかどうかで採用を判断することです。必要な領域に絞って導入し、イベントの設計とスキーマ進化の方針に最初から投資することが、成功への近道になります。
