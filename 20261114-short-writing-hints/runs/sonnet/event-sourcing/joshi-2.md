# イベントソーシング解説

## 1. イベントソーシングとは

イベントソーシング(Event Sourcing)は、システムの「現在の状態」ではなく、状態を変化させた「出来事(イベント)」を記録していくデータ管理の考え方である。現在の状態は、記録済みのイベントを先頭から順に適用して導き出す。

従来の CRUD 型アプリケーションでは、データベースの行を UPDATE で上書きする。この方式では最新の状態しか残らないため、「なぜその状態になったのか」という経緯が失われてしまう。これに対してイベントソーシングは、過去のイベントを変更も削除もせず、追記だけを行う。

銀行口座にたとえると分かりやすい。残高だけを保存するのが CRUD であり、入出金の明細をすべて保存して、必要なときに残高を計算するのがイベントソーシングである。

## 2. 基本的な構成要素

イベントソーシングは、次の要素で構成される。

- **イベント**:過去に起きた事実を表すデータである。`OrderPlaced` や `ItemAdded` のように過去形で命名し、一度記録したら変更しない。
- **イベントストア**:イベントを追記専用で保存するデータストアである。通常は、集約(後述)ごとの「ストリーム」として順序を保って管理する。
- **集約(Aggregate)**:ビジネスルールの整合性を守る単位である。コマンドを受け取ると、現在の状態に照らして検証し、問題がなければ新しいイベントを生成する。
- **プロジェクション**:イベントから読み取り用のデータを組み立てる仕組みである。画面表示や検索に適した形で、非同期に更新されることが多い。
- **スナップショット**:ある時点の状態を保存しておく最適化である。イベントが増えても、復元時は途中から再生すれば済む。

状態の復元は、「初期状態に対してイベントを順に適用する」という単純な関数の繰り返しで表現できる。

```ts
type Event =
  | { type: "Deposited"; amount: number }
  | { type: "Withdrawn"; amount: number };

type Account = { balance: number };

function apply(state: Account, event: Event): Account {
  switch (event.type) {
    case "Deposited":
      return { balance: state.balance + event.amount };
    case "Withdrawn":
      return { balance: state.balance - event.amount };
  }
}

const events: Event[] = [
  { type: "Deposited", amount: 1000 },
  { type: "Withdrawn", amount: 300 },
];

const current = events.reduce(apply, { balance: 0 }); // { balance: 700 }
```

`apply` は副作用を持たない純粋関数にしておく。そうすれば、同じイベント列から必ず同じ状態を再現できる。

## 3. 得られる利点

**完全な監査証跡。** すべての変更が事実として残るため、監査やコンプライアンス対応に強い。別途監査ログを実装する必要もなく、ログと実データが食い違う心配もない。

**過去状態の再現。** 任意の時点までのイベントだけを再生すれば、その時点の状態を復元できる。障害の原因調査や、「あの日の画面で何が見えていたか」の確認に役立つ。

**読み取りモデルの自由度。** イベントさえ残っていれば、後から新しい用途のプロジェクションを作り、過去の全イベントから再構築できる。集計や分析の要件が途中で変わっても、データを失っていないので対応しやすい。

**他システムとの連携。** イベントはそのまま外部へ通知する素材にもなる。マイクロサービス間の連携や、検索インデックス、データ分析基盤への反映を、同じイベント列から実現できる。

**CQRS との相性。** 書き込みはイベントの追記、読み取りはプロジェクションと役割を分けやすい。それぞれを独立してスケールさせられる。

## 4. 課題と注意点

利点が大きい反面、導入には相応のコストがかかる。

**スキーマの進化。** イベントは不変であるため、過去のイベントの形式を後から書き換えられない。仕様変更に備えて、バージョン番号を持たせたり、読み込み時に古い形式を新しい形式へ変換する「アップキャスト」を用意したりする必要がある。

**結果整合性。** プロジェクションが非同期に更新される場合、書き込み直後の読み取りに結果が反映されないことがある。UI の設計では、この遅延を前提にしなければならない。

**個人情報の削除。** 追記専用という性質は、GDPR などの「忘れられる権利」と衝突する。個人情報は暗号化して保存し、削除要求があれば鍵を破棄する「クリプトシュレッディング」が代表的な対処法である。あるいは、個人情報そのものをイベントに含めない設計にする。

**学習コストと設計の難しさ。** イベントの粒度や命名、集約の境界は、ドメインの理解に深く依存する。「ステータスが更新された」といった CRUD 的なイベントは、意図が読み取れないため避けたい。`OrderCancelled` のように、業務上の意味を持つ名前にする。

**運用面の負荷。** イベント数は単調に増え続ける。保存容量、再構築にかかる時間、スナップショットの運用を、あらかじめ見積もっておく必要がある。

## 5. 実装のポイント

**楽観的排他制御。** 同じ集約への同時更新を防ぐため、イベントの追記時に「期待するバージョン」を指定し、食い違っていれば失敗させる。失敗した場合は、最新の状態を読み直してコマンドを再実行する。

**イベントの発行と保存の一貫性。** イベントを保存しながら外部のメッセージブローカーにも送る場合、両者が食い違うおそれがある。イベントと同じトランザクションで「送信待ち」のレコードを保存し、別プロセスで送信する Outbox パターンが有効である。

**冪等なプロジェクション。** 配信は「少なくとも一度」になりやすく、同じイベントが重複して届くことがある。イベントのシーケンス番号を記録して、処理済みのものは読み飛ばせるようにしておく。

**スナップショットは後から追加する。** 最初から導入せず、再生に時間がかかり始めた段階で追加すれば十分である。スナップショットはあくまで最適化であり、正本はイベントである。

**ストレージの選択。** 専用製品としては EventStoreDB などがある。一方、PostgreSQL のような RDB に、ストリーム ID とバージョンの組を一意制約にしたテーブルを作る方法でも、小〜中規模なら実用に耐える。まずは使い慣れた基盤で始めるのが現実的である。

## 6. 採用判断の目安

イベントソーシングは万能ではない。次のような条件に当てはまるなら、検討する価値が高い。

- 変更履歴そのものが業務上の価値を持つ(金融、在庫、受発注、医療など)。
- 監査や説明責任の要件が厳しい。
- 状態遷移が複雑で、「なぜこうなったか」を追跡したい。
- 同じ事実から、複数の読み取りモデルや外部連携を派生させたい。

逆に、単純な管理画面や、履歴が不要な設定データのように、CRUD で十分な領域に導入すると、複雑さだけが増えてしまう。

また、システム全体に適用する必要はない。履歴が重要な一部の境界づけられたコンテキストだけに採用し、それ以外は従来どおりの方式で作るのが堅実である。小さな領域で試し、スキーマ進化や運用の勘所をつかんでから範囲を広げるとよい。
