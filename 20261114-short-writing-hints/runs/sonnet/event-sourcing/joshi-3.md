# イベントソーシング入門

## 1. イベントソーシングとは

イベントソーシング(Event Sourcing)は、アプリケーションの状態を「現在の値」ではなく「状態を変化させた出来事(イベント)の列」として保存する設計パターンである。

一般的な CRUD では、注文テーブルの 1 行を UPDATE で上書きするため、過去の値は失われる。これに対してイベントソーシングは上書きをせず、「注文が作成された」「商品が追加された」「支払いが完了した」といったイベントを追記のみで記録する。現在の状態は、イベントを先頭から順に適用(リプレイ)して導出する。

銀行口座が分かりやすい例だろう。残高 7,000 円という値だけを保存するのではなく、「10,000 円の入金」と「3,000 円の出金」という取引履歴を保存し、残高は履歴の集計として求める。会計の元帳と同じ考え方である。

イベントには次の性質がある。

- **過去形で命名する**:`Deposited` のように、すでに起きた事実を表す
- **不変である**:一度保存したイベントは書き換えない
- **順序を持つ**:アグリゲート(後述)ごとに、発生順で並ぶ

状態の導出は、純粋関数として次のように書ける。

```typescript
type AccountEvent =
  | { type: "Opened"; accountId: string }
  | { type: "Deposited"; accountId: string; amount: number }
  | { type: "Withdrawn"; accountId: string; amount: number };

type Account = { balance: number; open: boolean };

function apply(state: Account, event: AccountEvent): Account {
  switch (event.type) {
    case "Opened":
      return { balance: 0, open: true };
    case "Deposited":
      return { ...state, balance: state.balance + event.amount };
    case "Withdrawn":
      return { ...state, balance: state.balance - event.amount };
  }
}

const current = events.reduce(apply, { balance: 0, open: false });
```

## 2. 基本的な構成要素

イベントソーシングのシステムは、主に次の要素で構成される。

**イベントストア**は、イベントを追記専用で保存するデータベースである。専用製品(EventStoreDB など)のほか、RDB の追記専用テーブルでも実装できる。最低限必要なのは、アグリゲート ID ごとにイベントを順序どおり読み出せることと、追記時にバージョンの衝突を検出できることだ。

**アグリゲート**は、一貫性を保つ単位である。DDD の用語で、口座や注文などが該当する。イベントの順序保証と排他制御は、このアグリゲートの単位で行う。

**コマンド**は「出金せよ」のような意図の表明である。コマンドは拒否されることがあるが、イベントはすでに起きた事実なので拒否できない。この違いは設計上、重要である。

**プロジェクション**は、イベント列から作る読み取り用のビューである。画面表示や検索に適した形へ変換し、別のテーブルや検索エンジンに保存する。

**スナップショット**は、一定件数ごとに保存する状態の写しである。イベントが数万件に達するとリプレイが遅くなるため、最新のスナップショットから後ろだけを適用して高速化する。あくまで最適化であり、正本はイベント列のままである。

## 3. 書き込みの流れ

コマンドの処理は、おおむね次の順序で進む。

1. コマンドを受け取る
2. 対象アグリゲートのイベントを読み込み、状態を復元する
3. 現在の状態に対してビジネスルールを検証する(例:残高不足なら拒否)
4. 検証を通れば、新しいイベントを生成する
5. 「読み込み時のバージョン」を期待値として、イベントストアに追記する

手順 5 では楽観的排他制御を使う。他のリクエストが先に追記していた場合、期待バージョンが一致せず追記は失敗する。その際は状態を読み直してやり直すか、呼び出し元にエラーを返す。これにより、ロックを使わずに二重出金のような競合を防げる。

追記後に、プロジェクションがイベントを購読して読み取りモデルを更新する。この更新は非同期で行われるのが一般的で、書き込みの直後は読み取りモデルが古い可能性がある。

## 4. 利点

**完全な監査証跡が得られる。** 「いつ、何が、どの順で起きたか」がそのまま残る。金融や医療など、変更履歴の説明責任が重い領域では大きな強みになる。

**過去の状態を再現できる。** 任意の時点までのイベントだけを適用すれば、その時点の状態を復元できる。障害の調査や「あの日の残高はいくらだったか」という問い合わせにも答えられる。

**読み取りモデルを後から作れる。** 新しい集計や画面が必要になったとき、既存のイベントを最初からリプレイすれば、過去分も含めたビューを作れる。保存時に用途を決め打ちする必要がない。

**他システムとの連携が容易になる。** イベントはそのまま、メッセージングや他サービスへの通知の元データになる。

## 5. 課題と注意点

導入前に、次の難点を理解しておく必要がある。

**スキーマの進化が難しい。** イベントは不変なので、古い形式のイベントが永久に残る。フィールドの追加や意味の変更には、読み込み時に旧形式を新形式へ変換する仕組み(アップキャスト)が要る。最初からイベントにバージョンを持たせておくとよい。

**結果整合性を受け入れる必要がある。** 読み取りモデルは遅れて更新されるため、「書いた直後に画面で見えない」状況が起こりうる。UI の設計や利用者への見せ方で対処する。

**データの削除が難しい。** 個人情報の削除要求(GDPR など)があっても、イベントは書き換えられない。個人情報を暗号化して保存し、鍵を破棄することで読めなくする方法(クリプトシュレッディング)が知られている。

**学習コストと運用負荷が高い。** リプレイ、プロジェクションの再構築、イベント設計の見直しなど、CRUD にはない作業が発生する。また、イベントの粒度を誤ると、あとで修正しにくい。

## 6. 採用の判断基準

イベントソーシングは万能ではない。次の条件に当てはまるほど、採用する価値が高くなる。

- 変更履歴そのものが業務上の価値を持つ(監査、会計、在庫、予約など)
- 「なぜ今の状態になったか」を説明する必要がある
- 読み取りと書き込みで、求められるデータ構造が大きく異なる

逆に、単純な管理画面や設定データのように、履歴に価値がない領域では過剰になりやすい。

多くの場合、イベントソーシングは CQRS(コマンドと問い合わせの責務分離)と組み合わせて使われるが、両者は独立した概念である。まずは履歴の価値が高い一部のアグリゲートだけに適用し、システム全体を一度に切り替えないことをおすすめする。小さく始めて、イベント設計とスキーマ進化の運用に慣れてから範囲を広げれば、リスクを抑えられる。
