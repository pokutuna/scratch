# イベントソーシング入門

## 1. イベントソーシングとは

一般的なアプリケーションは、エンティティの「現在の状態」をデータベースに保存し、更新のたびに上書きします。この方式では、ある時点の状態は分かっても、どのような経緯でその状態に至ったのかは失われてしまいます。

イベントソーシング(Event Sourcing)は、状態そのものではなく、状態を変化させた「出来事(イベント)」を時系列に記録する設計パターンです。現在の状態は、保存されたイベントを先頭から順に適用(リプレイ)して導出します。

銀行口座を例に考えます。残高 8,000 円という値を保存する代わりに、「口座開設」「10,000 円入金」「2,000 円出金」というイベントを保存します。残高は、これらを順に適用した結果にすぎません。

イベントには次の性質があります。

- 過去に起きた事実を表すため、名前は過去形にする(`OrderPlaced`、`MoneyDeposited` など)
- 追記のみを許し、更新も削除も行わない(イミュータブル)
- 誤りを訂正するときは、元のイベントを書き換えず、取り消しや修正を表す新しいイベントを追加する

## 2. 基本的な仕組み

中心となる要素は、イベントストア、集約(Aggregate)、コマンドの 3 つです。

- **イベントストア**:イベントを追記専用で保存するストレージ。集約ごとのイベント列(ストリーム)を順序付きで保持する
- **集約**:一貫性を保つ単位。ビジネスルールを検証し、新しいイベントを生成する
- **コマンド**:「入金せよ」のように、変更の意図を表す要求。拒否される場合がある

状態の復元は、イベントに対する単純な畳み込みで書けます。

```ts
type AccountEvent =
  | { type: "AccountOpened"; accountId: string }
  | { type: "MoneyDeposited"; amount: number }
  | { type: "MoneyWithdrawn"; amount: number };

type Account = { balance: number };

function apply(state: Account, event: AccountEvent): Account {
  switch (event.type) {
    case "AccountOpened":
      return { balance: 0 };
    case "MoneyDeposited":
      return { balance: state.balance + event.amount };
    case "MoneyWithdrawn":
      return { balance: state.balance - event.amount };
  }
}

const account = events.reduce(apply, { balance: 0 });
```

コマンドの処理は次の流れで進みます。

1. 対象の集約のイベント列を読み込み、`apply` で現在の状態を復元する
2. 復元した状態に対してビジネスルールを検証する(例:残高を超える出金は拒否する)
3. 検証に通れば、新しいイベントを生成する
4. 読み込み時のバージョンを期待値として、イベントストアに追記する

手順 4 では楽観的排他制御を使います。期待するバージョンと実際のバージョンが異なる場合、別のコマンドが先に書き込んだことになるため、追記を失敗させて再試行します。これにより、ロックを使わずに集約の整合性を守れます。

イベント数が増えると、リプレイに時間がかかります。そこで、一定件数ごとに状態のスナップショットを保存し、復元時は最新のスナップショット以降のイベントだけを適用する最適化がよく使われます。スナップショットは、あくまで性能のためのキャッシュであり、正しさの根拠はイベント列にあります。

## 3. CQRS とプロジェクション

イベントソーシングは、CQRS(Command Query Responsibility Segregation)と組み合わせて語られることが多い手法です。イベント列は書き込みには向いていますが、「顧客別の売上一覧」のような検索や集計には向いていません。そのため、更新系と参照系のモデルを分離します。

参照系のモデルは、プロジェクション(リードモデル)と呼ばれます。イベントを購読して、検索に適した形(RDB のテーブル、検索エンジンのインデックス、キャッシュなど)に変換し、保存します。用途ごとに複数のプロジェクションを作れる点が特長です。

プロジェクションの更新は非同期で行うのが一般的です。そのため、書き込み直後に読み取っても、最新の内容が反映されていない場合があります。つまり、結果整合性を前提にした設計が必要です。画面側では、書き込み後に楽観的に表示を更新する、あるいは反映を待ってから遷移するといった工夫を要します。

また、プロジェクションはイベントから再生成できます。そのため、集計軸の追加や不具合の修正が必要になったときは、プロジェクションを作り直し、全イベントを再処理すれば済みます。

## 4. メリット

**完全な監査証跡が得られる。** すべての変更が理由とともに残るため、金融や医療のように説明責任が重い領域で役立ちます。履歴を別途ログとして実装する必要がなく、ログと状態が食い違うこともありません。

**過去の状態を再現できる。** 任意の時点までイベントを適用すれば、その時点の状態が得られます。障害調査では本番の経緯をそのまま再現でき、バグ修正後の再計算にも使えます。

**後から新しい用途に使える。** 保存済みのイベントは、将来の分析や新機能の入力にもなります。状態を上書きする方式では、捨てた履歴を取り戻せません。

**ドメインの表現力が上がる。** 「住所が変更された」と「住所の誤りが訂正された」は、状態だけを見ると同じ更新ですが、イベントでは区別できます。業務上の意味を、データとして保持できます。

## 5. 課題と注意点

**スキーマの進化。** イベントは不変であるため、過去のイベントの形式は変更できません。形式を変える場合は、読み込み時に旧形式を新形式へ変換するアップキャスト(upcasting)や、バージョン付きのイベント型で対処します。イベントは長期間残る公開契約と考え、設計の初期段階から慎重に命名し、項目を決めるべきです。

**結果整合性の扱い。** 前述のとおり、参照系は遅れて更新されます。ユーザーや他システムがこの遅延を許容できるか、事前に確認しておく必要があります。

**個人情報の削除。** 追記のみの原則は、GDPR などが求める削除要求と衝突します。代表的な対策は、個人情報を暗号化してイベントに含め、削除要求を受けたら鍵を破棄する方法(crypto shredding)です。あるいは、個人情報をイベントに含めず、別のストアで管理します。

**運用と学習のコスト。** 従来の CRUD に比べて、考え方も運用も複雑です。プロジェクションの再構築、イベントの再処理、重複配信への対応(冪等性の確保)など、考慮事項が増えます。チームが概念に慣れていない場合は、習熟に時間がかかります。

**粒度の設計。** `CustomerUpdated` のような粗いイベントは、CRUD の更新を記録しているだけで、意図が失われます。反対に細かすぎると、数が増えて扱いにくくなります。業務上意味のある単位で切ることが重要です。

## 6. 導入の判断基準

イベントソーシングは、すべてのシステムに適しているわけではありません。次の条件に当てはまるほど、導入の効果は大きくなります。

- 変更履歴そのものに業務上の価値がある(監査、会計、取引、在庫の増減など)
- 過去の状態の再現や、履歴に基づく分析が必要になる
- ドメインの複雑さが高く、イベントでモデル化すると理解しやすい

一方、単純な CRUD が中心の管理画面や、履歴が不要で結果整合性も許容できない小規模なシステムでは、複雑さに見合う利点が得られにくいでしょう。

導入する場合は、システム全体に広げず、履歴の価値が高い境界づけられたコンテキストに限定するのが現実的です。また、自前でイベントストアを実装せず、専用の製品(EventStoreDB など)や、既存の RDB 上のライブラリを使うと、排他制御や購読の実装コストを抑えられます。

まず小さな範囲で試し、イベントの設計や運用の知見を蓄積してから、適用範囲を広げることをお勧めします。
