# 静的な単語表による意味検索

[Modern Web Guidance の検索](https://github.com/GoogleChrome/modern-web-guidance-src/tree/main/src/rag)と同じ方式 (Model2Vec / Tokenlearn による静的な単語表と BM25 の合成) を、自分で一から組んで試す。元の実装の解説は [単語表だけで動く意味検索: Modern Web Guidance の静的埋め込み検索](https://claude.ai/artifact/QprH698TqnQuDFNDyXwWT8) にまとめた。文書はビルド時に Embedding モデルで埋め込み、クエリは「単語ごとのベクトルの表」を引いて足すだけでベクトルにする。実行時にモデルが要らないので、検索をブラウザ (`site/`) だけで動かせる。

- 教師モデル: [cl-nagoya/ruri-v3-310m](https://huggingface.co/cl-nagoya/ruri-v3-310m) (ローカルで実行、768 次元、クエリには `検索クエリ: `、文書には `検索文書: ` を付ける)
- データ (試すための題材): 2026-11-16 時点の [pokutuna の Scrapbox](https://scrapbox.io/pokutuna/) のエクスポート (JSON、9.7 MB、1,361 ページ)。`data/export.json` に置き、コミットしない

## 段階

コードは段階ごとに `scripts/s<N>_*.py` に分け、段階の順に読めば仕組みを追えるようにする。

| 段階 | スクリプト | 内容 |

共有するコード:

- `scripts/teacher.py`: 教師モデルの呼び出し

### 段階 1: チャンク化

Scrapbox には Markdown の見出しがないので、空行とインデントなしの `[* 見出し]` の行でブロックに分け、600 字を超えるまで前から詰めてチャンクにする。1,200 字を超えるブロックは、インデントなしの行 (アウトラインの親) の位置で分ける。各チャンクの先頭にはページのタイトルを付ける。

テキストからは次のものを除く。意味検索の雑音になり、埋め込みの長さも食うため。

- URL (`[URL タイトル]` はタイトルだけ残す)、アイコン (`[xxx.icon]`)
- `code:` ブロックの中身 (ファイル名の行は残す)
- 太字やリンクの括弧、`#` タグの `#`、引用の `>`

| 項目 | 値 |
| --- | --- |
| チャンク数 | 2,607 (1,361 ページ) |
| 文字数 | 約 155 万字 (記法と URL、コードを除いた後) |
| チャンクの文字数 | 中央値 641、90% 点 1,081、最大 2,592 |
| 1 チャンクだけのページ | 845 ページ |

### 段階 2: 文書の埋め込み

チャンクの先頭に `検索文書: ` を付けて ruri-v3-310m に通し、L2 正規化した 768 次元のベクトルにする。sentence-transformers を MPS (Apple Silicon の GPU) で動かし、2,607 チャンクで 109 秒 (1 秒あたり 24 チャンク) かかった。

無作為に選んだチャンク 2 つの cosine は平均 0.78 (10% 点 0.74、90% 点 0.82) で、無関係な文書同士でも高めに出る。検索では値そのものではなく順位を使う。

クエリも教師モデルで埋め込んで検索すると (`s2_teacher_search.py`)、言い換えたクエリでも目的のページが上位に来る。これが、後の段階で単語表に置き換えたときに目指す上限になる。

| クエリ | 1 位のページ (cosine) |
| --- | --- |
| 相手を賢く見せる言葉 | 賢そうな言葉 (0.871) |
| ログをエラーとして報告させる | Stackdriver Logging / ErrorReporting に標準出力/エラー出力を拾わせる (0.875) |
| pandas でデータを集計 | Numpy & Pandas (0.906) |

#### MLX を使わなかった理由

[mlx-embeddings](https://github.com/Blaizzy/mlx-embeddings) は ModernBERT に対応しているので、同じ 200 チャンクを埋め込んで比べた。1 秒あたり 21.6 チャンクで MPS (28.9) より遅く、MPS の出力との cosine も平均 0.87 (最小 0.76) と一致しなかった。プーリングかトークナイザの扱いが ruri-v3 の設定と違うと考えられる。速度の利点がないので、原因は追わずに sentence-transformers を使う。

### 段階 3: 単語表の初期値

#### 単語の分け方

日本語は `Intl.Segmenter` (ブラウザと Node に組み込みの、ICU の辞書による単語分割) で分ける。単語表は「語 → ベクトル」の表なので、ビルド時と検索時で区切り方が 1 文字でも違うと、その語のベクトルが使われない。そこで次のことを確かめた。

- `Intl.Segmenter` だけで分けると、Node 26 (ICU 78) と Chromium 156 で 326 チャンク中 162 件の結果が違った。違いはほぼすべて `package.json` や `code:x.go` のように `.` や `:` を含む英数字で、Node は 1 語に、Chromium は 2 語に分ける。日本語の部分の違いは 1 件だけだった
- 英数字の語を先に正規表現で取り出し、残りだけを `Intl.Segmenter` に渡すと、全 2,607 チャンクで Node、Chromium、JavaScriptCore (`jsc`、Safari と同じシステムのエンジン) の結果が一致した。Firefox は確かめていない

辞書にない語は `モー / ダル`、`賢 / く` のように崩れるが、ビルド時と検索時で同じように崩れるので、段階 4 の学習がその区切りに合わせて表を調整する。比べた文字 bigram は語彙が約 2 倍 (2 回以上出る語で 29,595) になるので使わなかった。

#### 語彙と初期値

チャンク全体に 2 回以上出る 15,724 語を語彙にする。各語を 1 語だけのクエリ (`検索クエリ: 汽水域`) として教師モデルに通したベクトルを単語ベクトルの初期値に、チャンクの集合での IDF を重みの初期値にする。IDF が最も小さい語は `ない`、`code`、`れ`、`さ` などで、よく出る語ほど和の中で軽く扱われる。

#### 学習前の結果

単語表で作ったクエリベクトルと、教師モデルのクエリベクトルの cosine は、8 件のクエリで平均 0.916 だった。値は高いが、上位のページは教師モデルの結果とかなりずれる。文書同士の cosine が 0.74〜0.82 に集まっているので、クエリベクトルが少しずれるだけで順位が入れ替わる。

| クエリ | 教師モデルの 1 位 | 単語表の 1 位 |
| --- | --- | --- |
| 相手を賢く見せる言葉 | 賢そうな言葉 | 賢そうな言葉 |
| pandas でデータを集計 | Numpy & Pandas | Numpy & Pandas |
| ログをエラーとして報告させる | Stackdriver Logging / ErrorReporting に… | A comprehensive taxonomy of hallucinations in… |
| 動画をプログラムで作る | キー表示付きの gif を作る | 見た 2026/11 |
| データ分析の可視化ライブラリ | Plotly | 定常性 |

`敬語の言い回し` は 2 語とも 1 回しか出ないので語彙に入らず、ベクトルを作れなかった。

### 段階 4: 単語表の学習 (Tokenlearn)

学習前の表は、語を 1 つずつ教師モデルに通しただけなので、複数語のクエリでは「単語ベクトルの和」と「クエリ全体を教師モデルに通したベクトル」がずれる。学習用クエリを用意し、各クエリについて両者の cosine が 1 に近づくよう、単語ベクトル e と重み w を勾配法で調整する。

```
L = Σ_t (1 - cos(q_t, y_t)) + μ/2 Σ_i ||e_i - e_i⁰||² + λ/2 Σ_i (w_i - w_i⁰)²
q_t = Σ_{i∈t} w_i e_i      (y_t は教師モデルのクエリベクトル)
```

第 2、第 3 項は、学習用クエリにあまり出てこない語が初期値から離れすぎないようにする正則化。最適化は Adagrad で、検証用クエリでの cosine が 2 エポック続けて良くならなければ止める。

#### 学習用クエリ

教師モデルさえあれば正解ラベルは要らない。クエリのテキストだけを用意すればよい。

- 合成 (`s4_queries_synth.py`): ページのタイトル、インデントなしの見出し、その 2 つをつないだもの。6,870 件。本文の語そのものなので言い換えに弱い
- LLM (`s4_queries_llm.py`): OpenRouter 経由で DeepSeek V4.1 Flash にページを読ませ、そのページを探す人が打ちそうなクエリを、本文にない語での言い換えを含めて書かせる。チャンク数に応じて 1 ページ 2〜4 件、1,361 ページで 3,029 件。API キーは環境変数 `OPENROUTER_API_KEY` から読む。結果は `queries/llm.jsonl` としてコミットしてあるので、API キーがなくても以降の段階を再現できる

LLM のクエリのうち、文字列のハッシュで決めた約 10% (299 件) は検証用として学習から除く。どのページを読んで書かれたクエリかが分かっているので、検索の正解としても使える。

#### 結果

合成のクエリだけで学習した表と、LLM のクエリも加えた表を比べた。

| 学習に使ったクエリ | 件数 | 学習で更新された語 | 検証用クエリでの cosine |
| --- | ---: | ---: | --- |
| 合成のみ | 6,763 | 4,089 (26%) | 0.911 → 0.946 (3 エポック) |
| 合成 + LLM | 9,491 | 5,349 (34%) | 0.911 → 0.954 (4 エポック) |

検証用クエリで、そのクエリを書かせたページが何位に来るかを比べた (`s4_compare_tables.py`)。

| クエリベクトル | Hit@1 | Hit@5 | Hit@10 | MRR |
| --- | ---: | ---: | ---: | ---: |
| 教師モデル (上限) | 68.6% | 88.0% | 91.6% | 0.774 |
| 単語表 (学習前) | 35.8% | 51.2% | 55.9% | 0.435 |
| 単語表 (合成のみ) | 51.2% | 72.9% | 80.6% | 0.614 |
| 単語表 (合成 + LLM) | 55.5% | 77.6% | 81.9% | 0.657 |

学習で cosine は 0.04 しか上がらないが、検索の成績は大きく変わる。段階 3 で見たとおり、文書同士の cosine が狭い範囲に集まっているので、クエリベクトルの小さなずれが順位に効く。LLM のクエリを加えると、合成のみより Hit@5 で 4.7 ポイント上がった。検証用クエリが LLM の書いたものなので、同じ書き方のクエリで学習した分だけ有利な点は割り引いて見る。以降の段階では合成 + LLM の表を使う。段階 3 の 8 件のクエリ (学習には使っていない) でも、教師モデルとの cosine の平均は 0.916 から 0.959 に上がった。

### 段階 5: 縮める (PCA と int8)

float32 のままだと、単語表 (15,724 語 × 768 次元) が 48 MB、文書ベクトル (2,607 チャンク) が 8 MB あり、ブラウザに送るには大きい。次の 3 つで縮める。

1. 重みの畳み込み: 文書の順位はクエリベクトルの大きさに左右されないので、検索時に正規化しなくてよい。すると `w_i × e_i` を 1 本のベクトルとして表に持てて、クエリは表の行を足すだけで作れる
2. PCA: 文書ベクトルの主成分の上位 d 個の軸に、単語表と文書の両方を射影する。射影後の文書は正規化し直す
3. int8: 行ごとに、絶対値の最大が 127 になる倍率で割って丸める。倍率は行ごとに float32 で持つ

| 設定 | 大きさ | Hit@1 | Hit@5 | Hit@10 | MRR |
| --- | ---: | ---: | ---: | ---: | ---: |
| 768 次元 float32 | 56.3 MB | 55.5% | 77.6% | 81.9% | 0.657 |
| 768 次元 int8 | 14.2 MB | 54.2% | 78.9% | 81.9% | 0.648 |
| PCA 384 次元 int8 | 7.1 MB | 55.2% | 78.3% | 82.3% | 0.655 |
| PCA 256 次元 int8 | 4.8 MB | 55.5% | 79.6% | 83.6% | 0.663 |
| PCA 128 次元 int8 | 2.4 MB | 55.2% | 77.6% | 82.6% | 0.648 |
| PCA 64 次元 int8 | 1.2 MB | 47.8% | 71.9% | 76.9% | 0.590 |

int8 にしても成績はほぼ変わらない。ruri-v3 は次元を切り詰めて使う学習 (MRL、Matryoshka Representation Learning) をしていないので先頭の次元を切るだけでは使えないが、PCA で軸を回してからなら 128 次元まで落ちない。256 次元の int8 (4.8 MB) を使う。成績の差は 299 件のクエリで数件分なので、128〜512 次元の違いは誤差の範囲と見る。

#### 元の実装、Model2Vec との違い

| 項目 | Modern Web Guidance | Model2Vec | この実装 |
| --- | --- | --- | --- |
| 次元の減らし方 | 先頭 256 次元を切る (教師の gemini-embedding-001 が MRL で学習されているのでできる) | PCA | PCA |
| PCA の軸を求めるデータ | - | 単語ベクトル (文書も同じ表で埋め込むので、表だけ射影すればよい) | 文書ベクトル。単語表と文書の両方に同じ軸を使う |
| int8 | 行ごとの対称量子化 | - | 同じ |
| 単語の倍率 | 行の倍率 × 重みを 1 語 1 つ持つ | - | 重みを掛けたベクトルを量子化するので同じ形になる |
| 文書の倍率 | チャンクごとに持つ | - | 同じ |

PCA は、MRL が学習で作る「情報の多い次元ほど前にある」並びを後から作る操作とみなせる。軸を回すだけなら単語表と文書の両方に同じ回転がかかり内積は変わらないので、効くのは後ろの次元を捨てる部分だけ。この実装では検索のスコアが文書ベクトルとの内積なので、文書の差がよく出る方向を残すよう、文書ベクトルで軸を決めた。単語表で軸を決める方法とは比べていない。

途中で 2 つ間違えたので、理由と合わせて残しておく。

- 文書ベクトルから平均を引いて射影し、正規化すると、768 次元のまま (軸を回すだけ) でも MRR が 0.657 から 0.609 に落ちた。平均を引くこと自体は、内積 `q·(d - m) = q·d - q·m` の `q·m` がどの文書にも共通なので順位を変えない。しかし平均を引いた後に正規化すると、文書ごとに違う倍率で割ることになり順位が変わる。軸は平均を引いて求めるが、射影は平均を引く前のベクトルに対して行う
- 文書の int8 の倍率を捨てて書き出したら、MRR が 0.185 になった。倍率は各行の絶対値の最大で決まり、文書ごとに違う。捨てると文書ごとに違う倍率を掛けたのと同じになる。文書の倍率も書き出し、スコアに掛ける

書き出すファイル (`--save`、合わせて 4.8 MB):

| ファイル | 中身 |
| --- | --- |
| `data/index_words.i8` | 単語表 (15,724 × 256、int8) |
| `data/index_word_scale.f32` | 語ごとの倍率 (float32) |
| `data/index_docs.i8` | 文書ベクトル (2,607 × 256、int8) |
| `data/index_doc_scale.f32` | 文書ごとの倍率 (float32) |
| `data/index_meta.json` | 次元数、行数 |

### 段階 6: BM25 と合成する (RRF)

単語表のベクトル検索は言い換えに強いが、表にない語や固有名詞の一致は拾えない。BM25 はその逆なので、両者の順位を RRF で合成する。

```
RRF(p) = 1 / (k + rank_ベクトル(p)) + α / (k + rank_BM25(p))      rank は 1 始まり
```

スコアの値ではなく順位だけを使うので、cosine (0.7〜0.9 に集まる) と BM25 (0〜数十) の尺度を合わせなくてよい。BM25 はチャンク単位で計算し (k1 = 1.2、b = 0.75)、ページのスコアはチャンクの最大値にする。単語分割は単語表と同じ `site/tokenize.mjs` で、語彙に入らなかった 1 回しか出ない語も BM25 では使える。ベクトル検索は段階 5 で書き出した int8 のファイルを使う。

検証用クエリ 299 件に加え、そのうち正解ページと語があまり重ならないもの (クエリの語のうち正解ページに出てくる語が 50% 未満、84 件) を言い換えのクエリとして別に集計した。

| 方式 | 全体 Hit@1 | 全体 Hit@10 | 全体 MRR | 言い換え Hit@5 | 言い換え Hit@10 | 言い換え MRR |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| BM25 | 64.5% | 81.9% | 0.706 | 32.1% | 40.5% | 0.260 |
| 単語表 | 55.5% | 83.6% | 0.663 | 52.4% | 61.9% | 0.371 |
| 単語表 + BM25 (k = 60、α = 1) | 59.9% | 83.9% | 0.689 | 36.9% | 47.6% | 0.275 |
| 単語表 + BM25 (k = 10、α = 1) | 60.2% | 89.3% | 0.701 | 40.5% | 65.5% | 0.300 |
| 単語表 + BM25 (k = 10、α = 0.5) | 59.2% | 87.6% | 0.700 | 47.6% | 63.1% | 0.342 |
| 教師 (参考) | 68.6% | 91.6% | 0.774 | 72.6% | 78.6% | 0.584 |
| 教師 + BM25 (k = 10、α = 0.5、参考) | 66.9% | 93.3% | 0.767 | 70.2% | 78.6% | 0.475 |

- 全体では BM25 単独の MRR が最も高い。LLM には本文を読ませてクエリを書かせたので、本文の語をそのまま含むクエリが多く、検証用クエリが BM25 に有利になっている
- 合成すると全体の Hit@10 は上がる (83.6% → 89.3%) が、言い換えのクエリでは上位の順位が単語表だけより悪くなる。言い換えのクエリでも、正解でないページがありふれた語の一致で BM25 の上位に来て、それが合成後の順位を押し上げていると考えられる (個々のクエリまでは確かめていない)。教師モデルと合成しても、言い換えの MRR は 0.584 から 0.475 に下がる
- よく使われる k = 60 は、上位の順位差を小さく扱うので、ここでは k = 10 より悪かった
- 全体と言い換えの両方で勝つ設定はない。k = 10、α = 0.5 を使う。全体の Hit@10 は合成の効果をほぼ残し、言い換えの Hit@5 の落ち方を半分ほどに抑える

検証用クエリは LLM が書いた 299 件だけで、言い換えに分類したのは 84 件しかない。自分が実際に打つクエリでの評価は、ブラウザで動かしてから確かめる。

### 段階 7: ブラウザで検索する

`site/index.html` で、クエリを入力するたびに検索する。計算は `site/search.mjs` にまとめ、段階 5、6 の Python と同じことをする。

1. `site/tokenize.mjs` でクエリを語に分ける
2. 単語表の行 (int8) に語ごとの倍率を掛けて足し、クエリベクトルにする。チャンクごとに int8 の内積を取り、チャンクの倍率を掛ける
3. BM25 の転置インデックスを引いて、チャンクのスコアを足し上げる
4. どちらもページのスコアはチャンクの最大値にし、2 つの順位を RRF (k = 10、α = 0.5) で合成する

結果にはページのタイトル、Scrapbox へのリンク、いちばんスコアの高いチャンクの先頭 120 字を出す。画面では、合成、単語表だけ、BM25 だけを切り替えられ、単語表にない語には取り消し線を引く。

`site/data/` に置くファイル (計 7.4 MB) は次のとおり。ページの本文は抜粋と BM25 の転置インデックス (語ごとの出現回数) としてだけ公開する。

本文中の git のコミット SHA (40 桁の 16 進数) は gitleaks がトークンと誤検知するので、抜粋では先頭 7 桁に縮め、BM25 の転置インデックスからは外す。

| ファイル | 大きさ | 内容 |
| --- | ---: | --- |
| `words.i8`、`word_scale.f32` | 4.09 MB | 単語表 (256 次元 int8) と語ごとの倍率 |
| `docs.i8`、`doc_scale.f32` | 0.68 MB | チャンクのベクトル (256 次元 int8) と倍率 |
| `vocab.json` | 0.19 MB | 単語表の語 (行の順) |
| `bm25.json` | 1.76 MB | 語 -> [チャンク番号, 出現回数, ...] と、チャンクの語数 |
| `pages.json` | 0.19 MB | ページのタイトル、URL、年 |
| `chunks.json` | 0.52 MB | チャンクのページ番号と抜粋 |
| `meta.json` | - | 次元数 |

検証用クエリ 299 件で、Node で動かした `search.mjs` の成績は Python (段階 6) と一致した。Chromium でも、3 つの方式すべてで上位 10 件が Node と同じになった。

| 方式 | Hit@1 | Hit@5 | Hit@10 | MRR |
| --- | ---: | ---: | ---: | ---: |
| BM25 | 64.5% | 77.9% | 81.9% | 0.706 |
| 単語表 | 55.5% | 79.6% | 83.6% | 0.663 |
| 単語表 + BM25 | 59.2% | 80.6% | 87.6% | 0.700 |

1 回の検索は 手元の Mac で 1.2〜1.8 ms (1,361 ページ、全チャンクとの内積を毎回計算する)。データの読み込みはローカルで 50 ms 程度。

```
uv run python scripts/s0_count_by_year.py data/export.json

```
